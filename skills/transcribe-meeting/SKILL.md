# 会議録音から議事録3点セット

音声ファイル1つから以下の3ファイルを自動生成するスキル。音声ファイルと同じフォルダに出力する。

| ファイル | 内容 |
|---------|------|
| `<stem>_transcript.txt` | 話者名付きトランスクリプト（原文・確度記号付き） |
| `<stem>_verbatim.txt` | ケバ取り版（フィラー除去・全内容保持） |
| `<stem>_summary.md` | 凝縮版（重複排除・小見出し付き段落再構成） |

`<stem>` は既定で音声ファイル名（拡張子除く）。ただし `Untitled` / `New Recording` / `IMG_1234` / `録音` 等、録音機器・OSの既定名（中身を表さない名前）の場合は、summary 生成時に内容から自動でタイトル・kebab-caseスラッグを生成し、3ファイル一式をそのスラッグにリネームする。

**`<stem>` に日本語（非ASCII）が含まれる場合も、内容を表す名前であってもリネームする**（齋藤指示 2026-08-05）。`YYYYMMDD-<内容の英語kebab-caseスラッグ>` を stem とし、区切りも kebab に揃えて `<stem>-transcript.txt` / `-verbatim.txt` / `-summary.md` とする。素材フォルダ・音声・チャンク（`parts/part00.m4a` 等）まで英語名にし、トランスクリプト本文の `## Part N — <チャンク名>` の参照も書き換える。日付は Step 1 で確定した実施日。

**工程の分担：Gemini API を使うのは音声を文字にする Step 2 だけ。** ケバ取り・凝縮（Step 4）は Claude 自身が行い、Gemini に投げない。音声を扱えるモデルが必要なのは文字起こしだけで、整形は契約済みの Claude で追加課金なくできる。実測では後処理が Gemini 課金の大半を占めていた（記録18件・1,464円のうち後処理が585円。ケバ取りは入力とほぼ同量を出力し、そこに thinking トークンが上乗せされる）。**2026-08-08 に後処理の Gemini 呼び出しをスクリプトから削除した**ので、後処理を Gemini に投げる手段はもう無い。

**Step 2 は無料枠だけで動かす**（齋藤方針 2026-08-05、2026-08-08 に徹底）。使うキーは `GEMINI_API_KEY_POOL` に列挙した無料枠キーに限り、課金キーはプールに入れない。**機密かどうかで課金キーへ振り分ける運用は行わない**（齋藤指示 2026-08-08）。無料枠が利用規約上、人間のレビュアーに入出力を読まれ得ることは変わらないので、その前提で扱ってよい音声かは録音・依頼の段階で判断する。

**成果物の整理**：Step 4 まで済んだら `--organize-only` で、`<stem>_summary.md` だけを直下に残し、音声・チャンク・中間txt（transcript/verbatim）・`<stem>_usage.json` を `<stem>/` サブフォルダに一括する（md 以外は素材フォルダにまとめる運用）。Step 2 の直後は summary が無いので整理せず、transcript を直下に残す（話者比定の作業用）。

**このSKILL.mdが置かれているディレクトリを基準に、`scripts/audio-transcribe.py` を実行すること。**

設計上の要点：**長尺音声を1ファイルで丸投げすると、モデルが途中で同一段落の反復ループに陥り後半を丸ごと欠落させる**。これを防ぐため、一定長を超える音声は最初から分割し、チャンクごとに品質を検査して破綻を検知したら再試行・再分割で回復する。

**429（quota）が出たら再実行しない。** スクリプトはプール内の次のキーへ自動で切り替えるので、止まったのは**プールの全キーで枠を使い切った**ときだけ。日次上限は当日中に回復しないため、枠リセット（太平洋時間0時＝日本時間16時頃）を待つか、無料枠キーをもう1つ増やす。成功チャンクはキャッシュされるので、再開しても再送信は起きない。無料枠の構造・キープールの組み方・本日消費のローカル集計は `references/quota-and-billing.md`。

## 使い方

```
/transcribe-meeting
```

引数なしで起動し、対話形式で情報を収集して処理を進める。

## Step 1: 情報収集

| 項目 | 必須 | 説明 |
|------|------|------|
| 音声ファイルパス | ○ | `.m4a` / `.mp3` / `.wav` 等 |
| 会議・録音の実施日 | ○ | 会話の文脈（「今日面談する」等）・ファイル名・指示から判断できなければユーザーに質問する。ファイルの更新日時（mtime）はコピー・同期等で実際の録音日とずれることがあるため、**それだけを根拠に確定しない**（一致を裏付けとして使うのはよいが、単独では採用しない） |
| 出席者リスト・議事次第 | △ | あれば話者比定の精度が大きく上がる（実名・所属・発言予定者） |
| スライド・配布資料 | △ | PDF 推奨。話題の担当が分かり比定・用語精度が上がる |
| 発表順・質問者氏名 | △ | 分かる範囲で |

出力先は音声ファイルと同じフォルダに固定（確認不要）。情報が揃ったら確認なしで処理を開始する。実施日はStep 3の凡例ブロックとStep 4のsummary冒頭に記載する。

## Step 2: 文字起こし

GEMINI_API_KEY が未設定なら `references/setup.md` を案内する。PPT が渡された場合は先に PDF 変換（`libreoffice --headless --convert-to pdf --outdir /tmp/ <ppt>`）。

**グロッサリ（文脈）ファイルを用意する**と固有名詞の誤認識を大幅に抑えられる。議事次第・出席者リスト・スライドから、主な発言者（実名・所属・役割）と専門用語の優先表記をテキストにまとめ、`--context` で渡す。例：`BRIDGE-X`（「ブリッジクロス」ではない）、`AND-E`（「アンディ」ではない）、`治験`（「知見」ではない）など、誤変換しやすい語を明記する。

文字起こしを実行する：

```bash
python3 <このSKILL.mdのディレクトリ>/scripts/audio-transcribe.py \
    <audio_file> --output <stem>_transcript.txt \
    --context <glossary.txt>
```

- **モデルは `gemini-3.5-flash-lite` の1つだけ**（齋藤指示 2026-08-08）。`--model` の選択肢もこれ1つで、格上げも格下げもしない。**単価と精度は連動しない**——Pro 系の出力には15分チャンク2本で各約6分の末尾欠落があり（被覆 61%・59%）、当時の緩い文字数チェックを素通りしていた。品質はモデルの格ではなく `check_quality` で担保する。フォールバック候補だった `gemini-3.1-flash-lite` も、書式崩れが再試行・再分割で回復せず不採用（実測の正本は ai-environment `docs/automation/20260804-transcription-model-comparison.md`）。
- **枠が尽きたらモデルではなくキーを替える。** 無料枠のクォータは「Cloud プロジェクト（キー）× モデル」単位なので、無料枠キーを増やせばそのぶん枠が増える。プールは `GEMINI_API_KEY_POOL="<ラベル> <ラベル>"` で宣言し、記載順に使う。
- **長尺は自動で分割モードに直行**。短い音声は単一ファイルで試し、品質不良なら分割へ切替。
- 各チャンクは **`check_quality`**（同一文字連続・**文/段落の反復ループ**・**短周期のピンポン型反復ループ**・**尺に対する文字数不足＝途切れ**・**尺に対する文字数過大＝内容捏造の疑い**・**タイムスタンプが尺の末尾まで届かない＝後半欠落**・**話者ラベル／改行の欠落**・短行過多）で検査し、失格なら **再試行 → 半分に再分割** で回復する。ただし書式崩れは再分割しても直らないため再試行のみに留める。
- 詳細と背景は [references/quota-and-billing.md](references/quota-and-billing.md)（無料枠の構造・キープールの組み方・品質チェックの内訳）。
- **このスクリプトは文字起こししかしない**。**話者比定（Step 3）を済ませてから** ケバ取り・凝縮を作る（Step 4）。
- 各 Gemini 呼び出しのトークン消費は `<stem>_usage.json` に記録される。**課金状態は実測しない**（プローブは 2026-08-08 廃止）。`GEMINI_API_KEY_POOL` に載せたキーを無料枠として扱い、レポートには `tier_source: declared` として残す。thinking（思考）トークンは出力単価で課金されるため、出力と混ぜず独立した項目で表示する（既定モデルでは 0 になる）。
- **実行ごとの明細は `~/.config/claude-toolkit/gemini-cost/<マシン名>.jsonl` に1行ずつ追記される**（案件・工程・モデル・thinking・品質）。累計は `scripts/gemini-cost-report.py` で見る（引数なしで工程別・案件別・日別・マシン別）。成果物を移動・削除しても履歴が残り、マシンをまたいだ合算もできる。

分割閾値・チャンク長・既定モデル名はスクリプト冒頭の定数が正本（`--help` に反映される）。**本ファイルに数値・モデル名を書かない**（二重管理で乖離する）。

## Step 3: 話者比定と確度付与

**未分離＝全編が話者A、でも実施する。** 出席者リスト・議事次第・スライドと、発言内の手がかりを突き合わせて各発言を発言者に対応づけ、**確度記号**を付す。

**★比定に着手する前に、参加者について事前に持っている情報（人脈・専門領域・所属・経歴等のメモ）があれば必ず先に確認する。** これを確認せずに「誰が言ったか／誰と誰が面識あるか」を割り当てると帰属を取り違えるリスクがある。名前が出た人物についての事前情報があれば、それを確認してから帰属を確定すること。自動ダイアライゼーションの話者ラベル（話者A/B）は**チャンク内外で入れ替わり得る**ので鵜呑みにせず、内容・専門知識・方言・人脈で照合する。

比定の手がかり（優先順）：
1. **明示的な自己紹介**「今年度担当の○○から」「○○大学の○○です」→ 確実
2. **司会の指名・引き継ぎ**「○○先生、お願いします」「○○部長よろしく」→ 直後の発言者が確定
3. **議事次第で発言者が制度上決まっている箇所**（挨拶＝○○PD 等）
4. **第三者言及**「○○さんと一緒に」→ その人は○○ではない
5. **スライド・話題の担当との整合／人称・文体**

**氏名・漢字は一次ソースから逐語コピーし、推測で確定しない。** 名字が一致しても別人の可能性があれば △ にとどめる。

**★話者ラベルに漢字を書く前に、その漢字の出所を確認する（当て字の再発防止・2026-07-27）。**
- **文字起こし本文に出てくる人名漢字を話者ラベルのソースにしない。** ASR は音声から漢字を推定する装置であり、人名は当て字になる（実例：ローマ字表記の姓を ASR が同音の別字で出力し、名簿の登録漢字と食い違った）。
- **出席者リスト・議事次第・プロジェクト md も、出所が併記されていなければ二次記述。** そこに漢字があっても、それだけを根拠に採用しない（実例：関係者表に載っていた名の漢字がメールアドレスのローマ字からの逆生成で、名簿の登録漢字とは別字だった）。
- 出席者のメールアドレスが分かるなら、**Contacts 系 MCP の検索で登録値（Name・Notes）を引く**のが最も速く確実。所属組織の名簿正本・本人のメール署名・researchmap も一次ソース。
- 引けなかった人物は**ローマ字またはカタカナのまま**ラベルにし、漢字に昇格させない。姓だけ一次で確認できている場合は姓のみ漢字にしてよい。
- 同姓の別人に注意（同じ会議に同姓で漢字表記の異なる2人が出た実例がある）。所属で切り分け、区別が必要なら凡例に一行注記を置く。

詳細は `~/.claude/PERSON-PROTOCOL.md` の R2-K・R2-S。

**★固有名詞（人名に限らず、専門用語・組織名・地名・研究課題名・製品名等）で `~/llm-wiki/` やプロジェクトmd等に参照が無いものは、確定前に軽くインターネットで照合する。** ASRは未知語を似た音の一般語や誤った専門用語に変換しやすい（例：治験→知見）。聞き取れた音から想定される候補語を1〜2件Web検索し、文脈（診療科・研究テーマ・所属組織等）と一致するか確認してから採用する。照合しても確証が持てない場合は通常の確度記号（△／？）で明示し、`[要確認]` を残す（推測で確定しない）。

### 確度記号

| 記号 | 意味 | 根拠 |
|---|---|---|
| ◎ | 確実 | 明示的自己紹介／司会の指名／議事次第で発言者が確定 |
| ○ | 推定・高 | 発言内容・所属・担当話題との整合で高確度 |
| △ | 推定・低／候補 | 手がかりが弱く氏名は仮（名字一致だが別人可能性 等） |
| ？ | 不明 | 比定不能＝話者不明 |

ラベル表記：`古賀部長〔◎〕:` `金子〔△・AMED担当と推定〕:` `話者不明〔？〕:`

トランスクリプト冒頭に**凡例ブロック**を置く：

```
# 凡例：話者ラベルの確度 ◎確実 ／ ○推定・高 ／ △推定・低（氏名は仮） ／ ？不明
# 自動文字起こしの校正物であり確定議事録ではない。
# 実施日：YYYY-MM-DD。
```

チャンク（`## Part N`）ごとに 話者A/B と実名の対応を決め、対応表JSONを書いて一括置換する。Part ヘッダー・区切り線は置換と同時に除去される。

```bash
cat > mapping.json <<'JSON'
{"1": {"話者A": "古賀部長〔◎〕", "話者B": "小西〔○〕"},
 "2": {"話者A": "小西〔○〕",     "話者B": "金子〔△・AMED担当と推定〕"}}
JSON
python3 <このSKILL.mdのディレクトリ>/scripts/apply-speaker-mapping.py \
    <stem>_transcript.txt --mapping mapping.json
```

- Part 分割が無い（未分離＝全編が話者A）場合は、キー `"0"` の対応表が全体に適用される：`{"0": {"話者A": "古賀部長〔◎〕"}}`
- 置換対象は行頭の `話者A:` 形式のみ。本文中で話者名に言及している箇所は書き換わらない。
- `--dry-run` で結果を標準出力に出して確認できる。既定で `.bak` を残す（`--no-backup` で無効化）。
- 未分離で1発言に複数話者が混在する場合は、この置換の後に発言単位で手作業ラベルを付す。

確信が持てない箇所は記号 △／？ で明示し、必要なら `[要確認: 推定 ○○]` を残す。

## Step 4: ケバ取り版・凝縮版の生成

**Gemini に投げず、Claude 自身が書く。** Step 3 で確定した実名・確度入りトランスクリプトを読み、`<stem>_verbatim.txt`（ケバ取り版）と `<stem>_summary.md`（凝縮版）を Write で作る。

**生成ルールの正本は `scripts/audio-transcribe.py` の `VERBATIM_PROMPT`（ケバ取り）・`CONDENSED_PROMPT`（凝縮）・`MERGE_PROMPT`（長尺を区間ごとに書いたときの統合）・`SUMMARY_REPAIR_PROMPT`（落ちた数値の補い方）。着手前にこの4つを読み、書かれている制約に従うこと。** 本ファイルにルールを写さないのは、同じ規則が2箇所にあるとズレるため（これらのプロンプトには、数値脱落を防ぐための構成・確度記号の扱い・省略禁止の根拠が実測つきで入っている）。スクリプト自身はこれらを送信しない——2026-08-08 に Gemini への後処理呼び出しを削除したので、**この4定数は Claude が読むためだけに置かれている**。

要点として押さえるべきは次の2つ。

- **事実を落とさない。** 削ってよいのは言い回しだけで、金額・数量・人数・日付・期限・割合・固有名詞・意思決定は原文の値のまま残す。概数へのぼかし（「数百万円」「複数台」）は禁止。
- **確度記号は凝縮版だけ簡略表記にする。** `〔◎〕`（確実）は付けない／`〔○〕`→`○`／`〔△〕`→`△`／`〔？〕`→`？`。transcript・verbatim は完全形 `〔◎〕〔○〕〔△〕〔？〕` を保持する。

書けたら**数値の欠落を機械で検査する**（API を呼ばないので無課金）：

```bash
python3 <このSKILL.mdのディレクトリ>/scripts/audio-transcribe.py \
    --check-numbers <stem>_transcript.txt <stem>_summary.md
```

要約は「短くする」ことに最適化されやすく、「省略厳禁」と書くだけでは金額・台数が落ちる（2026-08-04 の実測では予算面談の要約から 5000万・3800万・2500万・700万・500万・200万・123台 が丸ごと脱落し、保持率は35%だった。プロンプトを作り替えても70%で頭打ち）。**落ちた値が報告されたら、原文の該当箇所を確認して summary に補い、再度検査して0件にする。補い方は `SUMMARY_REPAIR_PROMPT` に従う**（既存の記述を書き換えず最小限の加筆で足す／原文の値をそのまま使う／文脈が判然としない値・聞き取り誤りと判断できる値は無理に入れない）。「原文に無いのに要約に現れた数値」の警告（合計値などの計算の可能性）は Step 5 で原文を確認する。

summary 冒頭には内容を表すタイトル（H1）を付ける（凡例のような定型文は要約の価値を薄めるので置かない）。**タイトル直後に、Step 1 で確認した実施日を1行入れる**（例：「実施日：2026-07-30。出席：○○・△△。」）。見出し自体に日付を入れない（`20260619-living-doc-structure.md` の見出し規約に合わせ、見出しは名詞句のみとし日付・確認情報は本文側に置く）。

3ファイルが揃ったら成果物を整理する（移動のみ・無課金）：

```bash
python3 <このSKILL.mdのディレクトリ>/scripts/audio-transcribe.py \
    --organize-only <stem>_transcript.txt
```

## Step 5: 完了報告

3ファイルのパスと行数、話者対応表（確度付き）、`[要確認]`／△／？ の箇所、**数値チェックの結果（補えなかった金額・台数／原文に無い数値）**、トークン消費・所要時間・品質評価（A/B/C）・無料枠の本日消費（`<stem>_usage.json`／末尾表示）を報告する。**課金額は Step 2 のぶんだけで、Step 4 は Claude 側なので Gemini の課金は発生しない。** 整理後は summary が直下、他は `<stem>/` にある。

Step 2 の実行直後の表示には、以下も出る（`<stem>_usage.json` の `keys_used` / `quality_detail` が同じ内容を持つ）。**報告にはこれらも含める。**

- **使用したアカウントとプラン** — キーのラベル・指紋（sha256 先頭8桁）・対応表に登録されたアカウント名／Cloud プロジェクト名、キーごとのリクエスト数とトークン数、プラン（無料枠／不明）。無料枠は「`GEMINI_API_KEY_POOL` への記載にもとづく宣言であって実測ではない」ことも併記される。対応表の作り方は [references/quota-and-billing.md](references/quota-and-billing.md)「ラベルとアカウントの対応表」。
- **区間別の品質と消費** — 区間ごとの尺・文字数・発話密度（字/秒）・判定（合格／回復(n回)／要確認／キャッシュ）・失格理由・その区間で消費したトークンと秒数・処理したキー。全体の A/B/C だけでは、どの区間が薄いのか・どこにトークンを使ったのかが分からないため。**判定は `check_quality` の機械判定であって、文字が正しいかは見ていない**——この区別を報告時に崩さない。
- **キーの宣言と記録の矛盾** — 無料枠と宣言したキーが `gemini-key-tier.json` に `paid` として記録されていれば警告が出る。出たらそのまま報告する（黙って実請求が始まる唯一の経路）。

```bash
open <stem>/<stem>_transcript.txt <stem>/<stem>_verbatim.txt <stem>_summary.md
```

## Step 6: 正本ディレクトリへの格納

音声ファイルの既定の置き場（Downloads 等）は一時置き場であり、最終保存先ではない。**Step 5 の完了報告時に、summary（および必要なら transcript/verbatim）を対象プロジェクトの正本ディレクトリへ移動することを必ず提案する。**

- ファイル名はプロジェクトのファイル命名規約に従う（例：確定日付＋会議名を前方 prefix にした `YYYYMMDD_<会議名>_summary.md`）
- 移動先プロジェクトが自明でなければ、Step 1 の情報収集時点でユーザーに確認する
- 音声・チャンク・中間txt・`<stem>_usage.json` が入った `<stem>/` 素材フォルダは機密性・容量の観点からリポジトリに含めない運用が一般的。移動する場合もプロジェクトの `.gitignore` 方針に従う
