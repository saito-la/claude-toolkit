# 会議録音から議事録3点セット

音声ファイル1つから以下の3ファイルを自動生成するスキル。音声ファイルと同じフォルダに出力する。

| ファイル | 内容 |
|---------|------|
| `<stem>_transcript.txt` | 話者名付きトランスクリプト（原文・確度記号付き） |
| `<stem>_verbatim.txt` | ケバ取り版（フィラー除去・全内容保持） |
| `<stem>_summary.md` | 凝縮版（重複排除・小見出し付き段落再構成） |

`<stem>` は既定で音声ファイル名（拡張子除く）。ただし `Untitled` / `New Recording` / `IMG_1234` / `録音` 等、録音機器・OSの既定名（中身を表さない名前）の場合は、summary 生成時に内容から自動でタイトル・kebab-caseスラッグを生成し、3ファイル一式をそのスラッグにリネームする（音声ファイル名が既に内容を表している場合はリネームしない）。

**成果物の整理（既定）**：派生生成まで済むと、`<stem>_summary.md` だけを直下に残し、音声・チャンク・中間txt（transcript/verbatim）・`<stem>_usage.json` を `<stem>/` サブフォルダに一括する（md 以外は素材フォルダにまとめる運用）。`--no-organize` で無効化。`--no-derive`（文字起こしのみ）では summary が無いため整理せず transcript を直下に残す（話者比定の作業用）。

**このSKILL.mdが置かれているディレクトリを基準に、`scripts/audio-transcribe.py` を実行すること。**

設計上の要点：**長尺音声を1ファイルで丸投げすると、モデルが途中で同一段落の反復ループに陥り後半を丸ごと欠落させる**。これを防ぐため、一定長を超える音声は最初から分割し、チャンクごとに品質を検査して破綻を検知したら再試行・モデル格上げ・再分割で回復する。

**429（quota）が出たら再実行しない。** 無料枠の日次上限は当日中に回復しないため、枠リセット（太平洋時間0時＝日本時間16時頃）を待つか billing を有効化する。成功チャンクはキャッシュされるので、再開しても再送信は起きない。無料枠の構造・本日消費のローカル集計・課金キーへの切り替えは `references/quota-and-billing.md`。

## 使い方

```
/transcribe-meeting
```

引数なしで起動し、対話形式で情報を収集して処理を進める。

## Step 1: 情報収集

| 項目 | 必須 | 説明 |
|------|------|------|
| 音声ファイルパス | ○ | `.m4a` / `.mp3` / `.wav` 等 |
| 会議・録音の実施日 | ○ | 会話の文脈（「今日面談する」等）・ファイル名・指示から判断できなければユーザーに質問する。ファイルの更新日時（mtime）はコピー・同期等で実際の録音日とずれることがあるため、**それだけを根拠に確定しない**（一致を裏付けとして使うのはよいが、単独では採用しない） |
| 出席者リスト・議事次第 | △ | あれば話者比定の精度が大きく上がる（実名・所属・発言予定者） |
| スライド・配布資料 | △ | PDF 推奨。話題の担当が分かり比定・用語精度が上がる |
| 発表順・質問者氏名 | △ | 分かる範囲で |

出力先は音声ファイルと同じフォルダに固定（確認不要）。情報が揃ったら確認なしで処理を開始する。実施日はStep 3の凡例ブロックとStep 4のsummary冒頭に記載する。

## Step 2: 文字起こし

GEMINI_API_KEY が未設定なら `references/setup.md` を案内する。PPT が渡された場合は先に PDF 変換（`libreoffice --headless --convert-to pdf --outdir /tmp/ <ppt>`）。

**グロッサリ（文脈）ファイルを用意する**と固有名詞の誤認識を大幅に抑えられる。議事次第・出席者リスト・スライドから、主な発言者（実名・所属・役割）と専門用語の優先表記をテキストにまとめ、`--context` で渡す。例：`BRIDGE-X`（「ブリッジクロス」ではない）、`AND-E`（「アンディ」ではない）、`治験`（「知見」ではない）など、誤変換しやすい語を明記する。

文字起こしを実行する：

```bash
python3 <このSKILL.mdのディレクトリ>/scripts/audio-transcribe.py \
    <audio_file> --output <stem>_transcript.txt \
    --context <glossary.txt> --no-derive
```

- **既定モデルは無料枠のある安価なモデル。品質不良時の自動格上げ先も無料枠のあるモデルで、無料枠を持たない高精度モデルへ勝手に移ることはない**（齋藤指示 2026-08-04）。高精度モデルは `--model` で明示指定する。`--no-escalate` で格上げ自体を止められる。**高精度モデルなら安全という前提は実測で否定されている**（Pro 系の出力にも15分チャンク2本で各約6分の末尾欠落があり、当時の緩い文字数チェックを素通りしていた）。品質はモデルの格ではなく `check_quality` で担保する。
- **長尺は自動で分割モードに直行**。短い音声は単一ファイルで試し、品質不良なら分割へ切替。
- 各チャンクは **`check_quality`**（同一文字連続・**文/段落の反復ループ**・**短周期のピンポン型反復ループ**・**尺に対する文字数不足＝途切れ**・**尺に対する文字数過大＝内容捏造の疑い**・**タイムスタンプが尺の末尾まで届かない＝後半欠落**・**話者ラベル／改行の欠落**・短行過多）で検査し、失格なら **再試行 → 格上げ → 半分に再分割** で回復する。ただし書式崩れは再分割しても直らないため再試行のみに留める。
- 詳細と背景は [references/quota-and-billing.md](references/quota-and-billing.md)（無料枠と課金枠の境界・**機密音声を無料枠へ送らない**・品質チェックの内訳）。
- `--no-derive` を付け、**話者比定（Step 3）を済ませてから** verbatim/summary を生成する（Step 4）。
- 各 Gemini 呼び出しのトークン消費は `<stem>_usage.json` に記録される。

分割閾値・チャンク長・既定モデル名はスクリプト冒頭の定数が正本（`--help` に反映される）。**本ファイルに数値・モデル名を書かない**（二重管理で乖離する）。

## Step 3: 話者比定と確度付与

**未分離＝全編が話者A、でも実施する。** 出席者リスト・議事次第・スライドと、発言内の手がかりを突き合わせて各発言を発言者に対応づけ、**確度記号**を付す。

**★比定に着手する前に、参加者について事前に持っている情報（人脈・専門領域・所属・経歴等のメモ）があれば必ず先に確認する。** これを確認せずに「誰が言ったか／誰と誰が面識あるか」を割り当てると帰属を取り違えるリスクがある。名前が出た人物についての事前情報があれば、それを確認してから帰属を確定すること。自動ダイアライゼーションの話者ラベル（話者A/B）は**チャンク内外で入れ替わり得る**ので鵜呑みにせず、内容・専門知識・方言・人脈で照合する。

比定の手がかり（優先順）：
1. **明示的な自己紹介**「今年度担当の○○から」「○○大学の○○です」→ 確実
2. **司会の指名・引き継ぎ**「○○先生、お願いします」「○○部長よろしく」→ 直後の発言者が確定
3. **議事次第で発言者が制度上決まっている箇所**（挨拶＝○○PD 等）
4. **第三者言及**「○○さんと一緒に」→ その人は○○ではない
5. **スライド・話題の担当との整合／人称・文体**

**氏名・漢字は一次ソースから逐語コピーし、推測で確定しない。** 名字が一致しても別人の可能性があれば △ にとどめる。

**★話者ラベルに漢字を書く前に、その漢字の出所を確認する（当て字の再発防止・2026-07-27）。**
- **文字起こし本文に出てくる人名漢字を話者ラベルのソースにしない。** ASR は音声から漢字を推定する装置であり、人名は当て字になる（実例：ローマ字表記の姓を ASR が同音の別字で出力し、名簿の登録漢字と食い違った）。
- **出席者リスト・議事次第・プロジェクト md も、出所が併記されていなければ二次記述。** そこに漢字があっても、それだけを根拠に採用しない（実例：関係者表に載っていた名の漢字がメールアドレスのローマ字からの逆生成で、名簿の登録漢字とは別字だった）。
- 出席者のメールアドレスが分かるなら、**Contacts 系 MCP の検索で登録値（Name・Notes）を引く**のが最も速く確実。所属組織の名簿正本・本人のメール署名・researchmap も一次ソース。
- 引けなかった人物は**ローマ字またはカタカナのまま**ラベルにし、漢字に昇格させない。姓だけ一次で確認できている場合は姓のみ漢字にしてよい。
- 同姓の別人に注意（同じ会議に同姓で漢字表記の異なる2人が出た実例がある）。所属で切り分け、区別が必要なら凡例に一行注記を置く。

詳細は `~/.claude/PERSON-PROTOCOL.md` の R2-K・R2-S。

**★固有名詞（人名に限らず、専門用語・組織名・地名・研究課題名・製品名等）で `~/llm-wiki/` やプロジェクトmd等に参照が無いものは、確定前に軽くインターネットで照合する。** ASRは未知語を似た音の一般語や誤った専門用語に変換しやすい（例：治験→知見）。聞き取れた音から想定される候補語を1〜2件Web検索し、文脈（診療科・研究テーマ・所属組織等）と一致するか確認してから採用する。照合しても確証が持てない場合は通常の確度記号（△／？）で明示し、`[要確認]` を残す（推測で確定しない）。

### 確度記号

| 記号 | 意味 | 根拠 |
|---|---|---|
| ◎ | 確実 | 明示的自己紹介／司会の指名／議事次第で発言者が確定 |
| ○ | 推定・高 | 発言内容・所属・担当話題との整合で高確度 |
| △ | 推定・低／候補 | 手がかりが弱く氏名は仮（名字一致だが別人可能性 等） |
| ？ | 不明 | 比定不能＝話者不明 |

ラベル表記：`古賀部長〔◎〕:` `金子〔△・AMED担当と推定〕:` `話者不明〔？〕:`

トランスクリプト冒頭に**凡例ブロック**を置く：

```
# 凡例：話者ラベルの確度 ◎確実 ／ ○推定・高 ／ △推定・低（氏名は仮） ／ ？不明
# 自動文字起こしの校正物であり確定議事録ではない。
# 実施日：YYYY-MM-DD。
```

チャンク（`## Part N`）ごとに 話者A/B と実名の対応を決め、対応表JSONを書いて一括置換する。Part ヘッダー・区切り線は置換と同時に除去される。

```bash
cat > mapping.json <<'JSON'
{"1": {"話者A": "古賀部長〔◎〕", "話者B": "小西〔○〕"},
 "2": {"話者A": "小西〔○〕",     "話者B": "金子〔△・AMED担当と推定〕"}}
JSON
python3 <このSKILL.mdのディレクトリ>/scripts/apply-speaker-mapping.py \
    <stem>_transcript.txt --mapping mapping.json
```

- Part 分割が無い（未分離＝全編が話者A）場合は、キー `"0"` の対応表が全体に適用される：`{"0": {"話者A": "古賀部長〔◎〕"}}`
- 置換対象は行頭の `話者A:` 形式のみ。本文中で話者名に言及している箇所は書き換わらない。
- `--dry-run` で結果を標準出力に出して確認できる。既定で `.bak` を残す（`--no-backup` で無効化）。
- 未分離で1発言に複数話者が混在する場合は、この置換の後に発言単位で手作業ラベルを付す。

確信が持てない箇所は記号 △／？ で明示し、必要なら `[要確認: 推定 ○○]` を残す。

## Step 4: ケバ取り版・凝縮版の生成

Step 3 で確定した実名・確度入りトランスクリプトから再生成する：

```bash
python3 <このSKILL.mdのディレクトリ>/scripts/audio-transcribe.py \
    --derive-only <stem>_transcript.txt
```

verbatim/summary は話者ラベルを継承する。**凝縮版（summary）だけは確度記号を簡略表記にする**：`〔◎〕`（確実）は付けない／`〔○〕`→`○`／`〔△〕`→`△`／`〔？〕`→`？`（transcript・verbatim は完全形 `〔◎〕〔○〕〔△〕〔？〕` を保持）。長尺は自動でブロック分割して処理（後処理でのループ・途切れを防止）。

**凝縮版には数値の欠落チェックが入る。** 要約は「短くする」ことに最適化されやすく、プロンプトで「省略厳禁」と書くだけでは金額・台数が落ちる（2026-08-04 の実測では予算面談の要約から 5000万・3800万・2500万・700万・500万・200万・123台 が丸ごと脱落し、保持率は35%だった）。そこで生成後に原文と突き合わせ、**落ちた金額・台数があれば原文の該当箇所を添えて1回だけ補完させる**（実測 35% →〔プロンプト改良〕70% →〔本チェック〕100%）。補完できなかった値と、**原文に無いのに要約に現れた数値**（合計値などモデルの計算の可能性）は警告として表示されるので、Step 5 で必ず原文を確認する。

summary は内容から生成したタイトル（H1）が自動で付く（凡例のような定型文は要約の価値を薄めるため自動付与しない）。**そのタイトル直後には、Step 1 で確認した実施日を1行で手動で入れる**（例：「実施日：2026-07-30。出席：○○・△△。」）。見出し自体に日付を入れない（`20260619-living-doc-structure.md`の見出し規約に合わせ、見出しは名詞句のみとし日付・確認情報は本文側に置く）。

（Step 2 で `--no-derive` を付けなかった場合は文字起こし直後に自動生成されるが、その場合 Step 3 の比定後に本コマンドで再生成すること。）

## Step 5: 完了報告

3ファイルのパスと行数、話者対応表（確度付き）、`[要確認]`／△／？ の箇所、**数値チェックの警告（補完できなかった金額・台数／原文に無い数値）**、トークン消費・所要時間・品質評価（A/B/C）・無料枠の本日消費（`<stem>_usage.json`／末尾表示）を報告する。整理後は summary が直下、他は `<stem>/` にある。

```bash
open <stem>/<stem>_transcript.txt <stem>/<stem>_verbatim.txt <stem>_summary.md
```

## Step 6: 正本ディレクトリへの格納

音声ファイルの既定の置き場（Downloads 等）は一時置き場であり、最終保存先ではない。**Step 5 の完了報告時に、summary（および必要なら transcript/verbatim）を対象プロジェクトの正本ディレクトリへ移動することを必ず提案する。**

- ファイル名はプロジェクトのファイル命名規約に従う（例：確定日付＋会議名を前方 prefix にした `YYYYMMDD_<会議名>_summary.md`）
- 移動先プロジェクトが自明でなければ、Step 1 の情報収集時点でユーザーに確認する
- 音声・チャンク・中間txt・`<stem>_usage.json` が入った `<stem>/` 素材フォルダは機密性・容量の観点からリポジトリに含めない運用が一般的。移動する場合もプロジェクトの `.gitignore` 方針に従う
