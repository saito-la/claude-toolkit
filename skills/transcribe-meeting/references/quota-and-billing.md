# Gemini API の無料枠と課金

随時更新（2026-08-08 時点）

実行時に必要な判断は SKILL.md の1行（429 が出たらプールの全キーを使い切った合図なので、枠リセットを待つか無料枠キーを増やす）で足りる。本ファイルはその背景と、枠が枯渇したときの調べ方をまとめたもの。

## 無料枠と課金枠の境界

**無料枠（Free Tier）とは、課金アカウントを紐づけていない Cloud プロジェクトのこと。** キーの形式（`AQ.` / `AIza`）では判別できない。課金を有効にしたプロジェクトは Tier 1 となり、無料の割当は無くなって最初のリクエストから課金される。

無料枠には1日リクエスト数（RPD）の上限がある。Google が随時改定しており、2026年には 20 → 250 → 1,500 と変動した報告がある。**2026-08 時点の公式ドキュメントは per-model の数値を掲載しておらず**、[AI Studio の Rate limit ダッシュボード](https://aistudio.google.com/rate-limit) で確認するよう案内している。**API は残枠を返さない。**

長尺音声は複数チャンク＝複数リクエストになる。そのため**失敗したジョブを丸ごと何度も再実行すると1日で枠を使い切る**。目安として、1時間の音声は15分チャンク5本＝5リクエスト・約12万トークン（音声は約25トークン/秒）。

## 枠の単位は「プロジェクト × モデル」

2026-08-08 に無料枠キーで 429 を起こして確認した。返るメトリクスに `model:` 次元が付く。

```
* Quota exceeded for metric: generativelanguage.googleapis.com/generate_content_free_tier_requests,
  limit: 0, model: gemini-3.1-pro
* Quota exceeded for metric: generativelanguage.googleapis.com/generate_content_free_tier_input_token_count,
  limit: 0, model: gemini-3.1-pro
```

つまり**リクエスト数もトークン数もモデルごとに別カウンタ**で、あるモデルの枠を使い切っても他モデルの枠は残る。ただし枠のキーは**エイリアスではなくベースモデル**である（`gemini-3.1-pro-preview` に投げたのに `gemini-3.1-pro` が返っている）。同じベースモデルを指す別名は同じ枠を食う。

**この構造から取れる手は2つある。** 他モデルへ逃げるか、他キー（別 Cloud プロジェクト）へ逃げるか。本スキルは**キーへ逃げる**方を採った——品質を満たす代替モデルが存在しないため（下記「モデルは1つだけ」）。

## キープールの組み方

`GEMINI_API_KEY_POOL` にラベルを空白区切りで並べる。スクリプトは記載順に使い、枠上限に当たったら次のキーへ自動で切り替えて同じリクエストを再試行する（試行回数は消費しない）。

```sh
export GEMINI_API_KEY_NHO="..."
export GEMINI_API_KEY_SAITOLA="..."
export GEMINI_API_KEY_POOL="NHO SAITOLA"     # この順に使う
```

**ここに載せるのは無料枠キーだけ。** 課金状態の実測プローブは 2026-08-08 に廃止したので、課金キーを混ぜても検出されず、無料枠が尽きた瞬間に黙って実請求が始まる。`GEMINI_API_KEY_POOL` への記載は「これは無料枠キーである」という利用者の宣言として扱われ、レポートには `tier_source: declared` として残る。

**未設定にしてはいけない**（複数キーがある環境では）。未設定時は `GEMINI_API_KEY_*` を自動検出するフォールバックに落ちるが、その順序は環境変数名のアルファベット順で、しかも `GEMINI_API_KEY`（＝既定キー）が先頭に来る。既定キーが課金キーだと、無料枠に手を付ける前に課金が走る。

## thinking トークンが課金の主役になる

**Gemini の思考トークン（`thoughts_token_count`）は応答本文（`candidates_token_count`）に含まれないが、出力単価でそのまま課金される。** 本スクリプトは `thinking_config` を指定せずモデル既定に委ねているため、量はモデルによって大きく違う。

- `gemini-3.5-flash-lite`（現在の唯一のモデル）・`gemini-2.5-flash`・`gemini-pro-latest` — thinking は 0
- `gemini-3.5-flash`（2026-08-08 まで品質不良時の**格上げ先**だった）— 出力の10〜25倍の thinking が発生する

実測（2026-08-05 集計・18件1,464円）では thinking が総額の **41%**。格上げが起きた実行では **64〜73%** を占めた。1リクエストで思考62,912トークン（289秒）を消費した例、**実質1秒の無音チャンクに思考11,885トークンを2回**費やした例がある。

**したがってコストは音声の長さでは決まらず、品質ゲートに何回引っかかったかで決まっていた。** 同じ規模の音声で、lite が一発合格した55分は14円、格上げが連鎖した92分は690円（1時間あたり15円 対 450円）。**この跳ね上がりの経路は 2026-08-08 の格上げ廃止で塞がれた。** 現在の唯一のモデルは thinking を出さない。

**同一入力の再試行は同じ結果を返すことがある**（実測でトークン数が完全一致する組が複数）。その場合リトライは枠を空費するだけになる。要確認が多発する音声は、再実行より録音品質・チャンク長の見直しが効く。

## 後処理を Gemini でやらない

**Gemini に投げるのは文字起こし（音声→文字）だけ。** ケバ取り・凝縮・タイトル生成は Claude 側で行う（齋藤方針 2026-08-05）。音声を扱えるモデルが必要なのは文字起こしだけで、整形は契約済みの Claude で追加課金なくできる。実測では後処理が Gemini 課金の大半（18件1,464円のうち585円。61分の会議1件では総額177円のうち162円）を占めていた——ケバ取りは入力とほぼ同量のテキストを出力し、そこに thinking が上乗せされるため。

**2026-08-08 に該当する Gemini 呼び出しをスクリプトから削除した**（`--derive` / `--derive-only` も廃止）。生成ルールを書いたプロンプト定数（`VERBATIM_PROMPT` 等）はスクリプト内に残してあるが、これは送信用ではなく **Claude が読むための正本**である。

**Step 2 は無料枠だけで動かす。** 1時間の音声は15分チャンク×4＝4リクエスト・約9万入力トークンで、無料枠の RPD には桁で余裕がある。

## 無料枠と機密の扱い

[Gemini API 利用規約](https://ai.google.dev/gemini-api/terms)は、無料枠（Unpaid Services）について「human reviewers may read, annotate, and process your API input and output」と定め、「Do not submit sensitive, confidential, or personal information to the Unpaid Services」と明示している。課金枠（Paid Services）では「Google doesn't use your prompts … or responses to improve our products」とされ、ログも規約違反検知目的に限定される。

**この事実を前提に、機密かどうかでキーを振り分ける運用は行わない**（齋藤指示 2026-08-08）。全ての音声が無料枠キーで処理される。したがって**無料枠に出せない音声は、このスキルに通さない**という判断を録音・依頼の段階で行う。スクリプト側に機密の分岐は無く、実行時の表示にも判断材料は出ない。

**課金状態は実測しない。** 無料枠を持たないモデルへ ping を投げて判定するプローブは 2026-08-08 に廃止した（プールを無料枠キーに限る運用にしたため、実行ごとに測る必要が無くなった）。`gemini-key-status.py` もキーが使えるかだけを見て、課金状態は返さない。疑わしいときは <https://aistudio.google.com/billing> を直接見る。

## 枯渇を防ぐ仕組み

スクリプト側に実装済みで、利用者が意識する必要はない。

1. **キーの自動ローテーション** — 日次上限・クレジット枯渇の 429 を受けたら、`GEMINI_API_KEY_POOL` の次のキーへ切り替えて同じリクエストを再試行する（試行回数は消費しない）。全キーを使い切って初めて停止する。
2. **成功チャンクのキャッシュ** — 各チャンクの結果を `<chunk>.txt` に保存し、再実行時は再送信しない。ただし品質チェックを満たさないキャッシュは破棄して取り直す。
3. **429 の原因別停止** — 前払いクレジット枯渇（購入するまで回復しない）と無料枠の日次上限（翌日回復）を区別して即停止する（`QuotaExhaustedError`・exit 2）。対処が正反対なので推測しない。分次レート制限と 503 のみ限定的にリトライする。
4. **既定チャンク長15分** — リクエスト数が無用に増えないための既定値。`--chunk-minutes` で変更できる。
5. **書式崩れでは再分割しない** — 話者ラベル・改行が落ちた区間は、短く割り直しても同じモデルが同じ書式で返す。再試行のみに留めてリクエストの空費を防ぐ。

本日の消費は実行末尾に「モデル × キー」別で出る（枠の単位と一致させてある）。ただしこれは当ツール経由・その Mac だけの集計で、他の Mac の消費は同じ枠を食うのに合算されない。**枠の判定にこの数字を使わない。**

## モデルは1つだけ

**`gemini-3.5-flash-lite` のみを使う**（齋藤指示 2026-08-08）。`--model` の選択肢もこれ1つで、格上げも格下げも行わない。枠が尽きたときはモデルではなくキーを替える。

比較の正本は ai-environment `docs/automation/20260804-transcription-model-comparison.md`（同一音声61分・同一チャンク・キャッシュを排して各モデルで取り直した実測）。要点は3つ。

- **単価と精度は連動しない。** 最高単価の `gemini-pro-latest` は15分チャンク2本で各約6分の末尾欠落を出した（被覆 61%・59%）。しかも当時の緩い文字数チェックを素通りして合格扱いでキャッシュされ、再実行しても不良出力が再利用される状態だった。
- **`gemini-3.1-flash-lite` はフォールバックにもしない。** 5チャンク中2本で改行と話者ラベルを落とし、再試行2回＋2段の再分割（計7回）すべてで同じ1行出力を返した。内容は取れているのに書式の指定だけを一貫して無視する。実運用では21リクエスト・8分37秒を費やして要確認2区間が残る（`gemini-3.5-flash-lite` は6リクエスト・4分で全区間合格）。**枠を3.5倍食って結果が悪い**ので、枠が尽きたときの逃げ先として成立しない。
- **固有名詞の精度には差が出なかった。** 敬称付き人名候補は7種中5種、カタカナ語は33種中24種が一致。どちらも `--context` での用語注入と人手確認が前提になる。

品質はモデルの格ではなく下記のチェックで担保する。

## 品質チェック

各区間について、反復ループ・同一文字の連続・尺に対する文字数の下限と上限（無音区間からの内容捏造の検知）に加えて、次を検査する。

- **タイムスタンプ被覆** — 最終 `[MM:SS]` が区間の尺の 75% に届かなければ末尾欠落とみなす。文字数の下限だけでは緩すぎて後半の欠落を通してしまう。
- **書式** — 改行が無い（5行未満）／話者ラベルが3個未満なら失格。後段の話者比定が成立しなくなるため。60秒未満の端切れ区間は免除する。
- **1塊出力の自動修復** — 改行が落ちていてもタイムスタンプが5個以上あれば、その直前で改行して行に戻す（再試行より確実で無料）。

## 429 が出たときの対応

再実行しても状況は変わらない。次のいずれかを選ぶ。

- **枠リセットを待つ** — 太平洋時間0時、日本時間では16時頃。
- **billing を有効化する** — 恒常的に使うならこちら。無料枠の `AQ.` 形式トークンが環境変数に入っている場合があるので、billing を有効にした `AIza…` 形式のキーを `~/.config/claude-toolkit/gemini-api-key` に置くのが確実。

**購入前に必ず確認する：** 複数アカウントのキーを使い分けている場合、429 は「課金が枯渇した」とは限らない。`env | grep GEMINI_API_KEY` で実際に使われているキー／アカウントを確認し、無料枠（Workspace等）のキーが使われているなら日次上限の可能性が高く、課金とは無関係（枠リセット待ちで解決）。`~/.config/claude-toolkit/gemini-usage.json`（直近14日のローカル集計）でトークン数を概算コスト換算し、実際に課金アカウントの残高が減るような消費量かを桁で確認してから購入判断をする。個人環境固有の対象アカウント・確認URLは各自の環境設定ドキュメントを参照。

## 累積コストログ

実行ごとに1行、`~/.config/claude-toolkit/gemini-cost/<マシン名>.jsonl` へ追記される（案件名・工程別・モデル別・thinking の内訳・格上げ回数・品質グレード・所要時間・課金状態）。閲覧はこれ1つで足りる。

```bash
python3 <skillのディレクトリ>/scripts/gemini-cost-report.py           # 工程別・案件別・日別・マシン別
python3 <skillのディレクトリ>/scripts/gemini-cost-report.py --days 7  # 直近7日
python3 <skillのディレクトリ>/scripts/gemini-cost-report.py --calls    # 案件ごとの工程内訳
```

- `<stem>_usage.json` は成果物と一緒に移動・削除されるため履歴が残らない。累積ログは追記専用で消えない
- **マシンごとに別ファイル。** 同一ファイルへ複数マシンから追記すると同期時に必ず衝突する。ディレクトリを git 等で同期すれば全マシン分が合算表示される（同期の配線は各自の環境側で行う）
- 散在する `_usage.json` の取り込みは `backfill-cost-log.py`。2026-08-04 より前の記録は thinking が未計上なので下限値として表示される
- **この集計を残高・無料枠の判定に使わないこと。** 同期していないマシンの消費は入らない。判定は `gemini-key-status.py` の実測を使う

## 本日消費のローカル集計

末尾のコスト表示は課金状態で文言が変わる。課金キーなら `実請求 約 N 円`、無料枠キーなら `実請求なし（無料枠。課金なら N 円相当）`。判定できなかった場合のみ「概算」に留まる。`<stem>_usage.json` には `billing_tier` と `billed` が入る。

実行末尾に「本日消費（ローカル集計・太平洋時間基準）」を表示する。当ツール経由のリクエスト数・トークン数を `~/.config/claude-toolkit/gemini-usage.json` に PT 日付ごとに積算し、`本日 N / 目安RPD（残り約M）` の形で出す。

- RPD 目安の既定は flash = 250。**これは推測値**（公式は per-model の数値を公開していない）。`--rpd N` または環境変数 `GEMINI_FLASH_RPD` で上書きする。
- **この集計を枠・残高の判定に使わないこと。** 当ツール経由・そのマシンだけの記録であり、他のアプリの消費も、同じキーを使う他のマシンの消費も含まれない。無料枠は API キー（Cloud プロジェクト）単位なので、どのマシンから投げても同じ枠を食う。
- 実際に使えるかどうかは `gemini-key-status.py` が各キーに ping を投げて実測する。残枠の数値はダッシュボードで確認する。
