# pj

今いる Claude セッションの中から「別のプロジェクトで作業を始めたい」と伝えられたときに、①現在のセッションの文脈で最適な既存プロジェクトを判断し、②新規 iTerm2 ウィンドウをそのディレクトリで開いて `claude` を新規起動するスキル。今のウィンドウはそのまま残る。Orca が動いている Mac では、iTerm2 の窓の代わりに Orca の作業場を作って起動する（`pj-open.sh` が `pj-orca.sh` へ渡す。Orca の入れ方は claude-toolkit の `tools/orca/README.md`）。

使う人は常にどこかの Claude セッションの中におり、シェルからプロジェクトを開き直す手間を省くための入口を Claude 側に用意するのが本スキル。

仕組み（判定の層・CLAUDE.md の書き方・Orca で開く・学習）と、そう作った理由は同じフォルダの `README.md`。

以下 `$SKILL` はこの SKILL.md が置かれているディレクトリの絶対パス。symlink 経由で読み込まれていても実体のディレクトリを解決して使う。

## 前提

- Mac で使う。開く先は Orca（動いていれば）か iTerm2。どちらも無い端末では開かない
- 行き先の候補は `~/Projects` の下で `CLAUDE.md` を持つフォルダ（深さ5まで）。`CLAUDE.md` の「目的」「切り分け／使い分け」の節と、先頭の frontmatter（`aliases` など）が索引になる。`.pjignore` を置いたフォルダは候補から外れる
- 索引は `~/.cache/pj/`、選んだ文の学習は `~/.local/state/pj/`（環境変数 `PJ_STATE_DIR` で変えられる）に置く。学習にはクエリ文がそのまま残るので、git には入れない

## 使い方

```
/pj <やりたいこと>        # 例: /pj 安全性報告の様式を直したい
```

またはチャットで「○○の作業を別で始めたい」「△△のプロジェクトを開いて」等、別プロジェクトでの起動意図が明確な発言でも同様に動作する。単なる話題の言及（今のセッションで続けられる話）では発動しない。

## 判定・起動フロー

**まず必ず高速パスを1回だけ叩く。** ドンピシャ引数（語彙が決定的一致）なら、これ1コマンドで確認・ナレーションなしに即起動する。往復を積まないこと。

```bash
bash "$SKILL/scripts/pj-go.sh" "<原文クエリ>"
```

出力1行目で分岐する：

1. **`OPENED<TAB><relpath>`** → 既に起動済み。**追加のコマンド・relpath実在確認・索引読みは一切行わない。** ユーザーへは `pj-open.sh` が標準エラーに出した1行（Orca の作業場か新規ウィンドウか、依頼文を渡したか）をそのまま返して終了する。原文に用件があれば、末尾に振り分けの1行を付けて開いた先への最初の指示として渡っている。「（依頼文を渡した）」が無いときは原文が行き先の名前だけだったので、用件を向こうで伝えてもらう旨を1行添える（今の作業の続きを向こうで実施する場合は、下の「作業を移すときの引き継ぎ」に従う）。

2. **`CANDIDATES`**（2行目以降 `<relpath>\t<reason>`）→ 語彙一致が複数あり確信が割れている。会話の流れ・グローバル/プロジェクト CLAUDE.md・memory など**カタログに載っていない知識も使って**最適なプロジェクトを判断する（この文脈判断がコマンドの主眼）。`CANDIDATES` は参考。
   - 1件に確信が持てる → そのまま起動（下記）。
   - **確信が持てないときだけ**、上位2〜3件を1行ずつ短く提示して選んでもらう。選択後に起動。

3. **`CATALOG`**（2行目以降が全プロジェクトの圧縮カタログ）→ 語彙一致なし。カタログ（約4kトークン）が出力に含まれているので、**追加のファイル読み込みはせず**その場で会話文脈と突き合わせて判断する。
   - **カタログは文字N-gram の類似度順に並んでいる**（先頭ほど有望）。ただし語彙一致ではないので確定情報ではない。会話文脈が別のプロジェクトを指すなら、順位を無視して文脈を優先する。
   - 妥当な候補がある → 起動。
   - どれも当てはまらない → 新規プロジェクト作成をユーザーと相談する。

CANDIDATES/CATALOG から手動で起動するときは、**`--query` に原文をそのまま渡す**：

```bash
bash "$SKILL/scripts/pj-open.sh" <relpath> --query "<原文クエリ>"
```

`--query` を渡すと「この文でここを選んだ」が `pj-learn.py` に記録され、次に似た言い回しで打ったとき候補の上位に来る。原文は高速パスと同じく、開いた先への最初の指示にもなる。**語彙一致が外れた（CANDIDATES/CATALOG だった）ときだけ渡す。** 高速パスが `OPENED` を返した場合は既に語彙一致で当たっているので、渡さない（渡すとよく使うプロジェクトの照合テキストだけが太り、何にでも当たるようになる）。

起動後の報告は 1 と同じ。

## 作業を移すときの引き継ぎ

単に別プロジェクトを開くのではなく、今の作業の続きを向こうで実施する場合は、次の3つを順に行う（3つ目が起動になる）。原文だけでは今の作業の文脈が渡らず、向こうのセッションは文脈ゼロから始まる。

**1. 同じリポジトリの中へ移すなら、書いた内容を先にコミットする。** `pj-open.sh` は専用 worktree を HEAD から作って開くため（2026-08-29 以降）、未コミットの追記は開いた先に存在しない。別リポジトリのプロジェクトへ移すときは関係ない。

**2. 移す先のプロジェクトの `action-items.md` に続きの行動を書く。** 書式と「書ける内容」の基準は `~/.claude/conventions/action-items-convention.md` が正本。設計・実測値・仕様は action-items に書かず、そのプロジェクトの正本文書（`README.md`・`docs/` 配下）に置き、節頭の `正本：` 1行で参照させる。向こうのセッションが最初に読むのは `CLAUDE.md` と `action-items.md` なので、**この2つから正本へ辿れる状態にして初めて引き継ぎが成立する。**

**3. 起動文を最初の指示として渡して開く。** 起動文をファイル（一時置き場でよい）に書き、`--prompt-file` で渡す。開いた先の claude は起動と同時に受け取るので、貼り付けは要らない。末尾には振り分けの1行が足される。

```bash
bash "$SKILL/scripts/pj-go.sh" "<原文クエリ>" --prompt-file <起動文のファイル>
# OPENED でなければ、選んだ行き先へ
bash "$SKILL/scripts/pj-open.sh" <relpath> --query "<原文クエリ>" --prompt-file <起動文のファイル>
```

起動文は固定文にしない。**最初に読むべき正本の場所と、最初の一手**が分かる文にする。

```
line-assist を実装したい。設計と実測は automation/line-assist/README.md、次の作業は automation/action-items.md の「line-assist の実装」節にある。
```

action-items.md だけで十分辿れるなら短くてよい。

```
action-items.md の最優先事項を実施して
```

起動後は、開いた先の `<relpath>` と、渡した起動文の全文を報告する。ファイルは起動後に消えるので、何を渡したかを後から確かめられるのはこの報告だけになる。

## 誤起動の修正

起動直後に「違う」「それじゃない」「正しくは ○○」等の訂正を受けたら、正しいプロジェクトを開き直す：`bash "$SKILL/scripts/pj-open.sh" <正relpath> --query "<原文クエリ>"`。

誤って開いたウィンドウは**自動で閉じない**（破壊的操作を避ける）。ユーザーに手動で閉じてもらうよう促す。

**開き直しと同じターンの中で、下記の恒久是正まで必ず済ませる。** 繰り返しを待たず、1件目の誤起動で行う。

## 開いた先での訂正

開いた先のセッションで行き先の誤りに気づくこともある。最初の指示の末尾に「（振り分け：「<原文>」から <relpath> を選んで開いた。…）」の1行があるセッションで、「ここではない」「別のプロジェクトだ」等と言われたら、開いた側（/pj を打ったセッション・planner の受付）に戻さず、そのセッションの中で次を行う。

1. 正しい行き先を決め、受けた依頼を渡して開き直す。最初の指示から振り分けの1行を除いた本文をファイルに書き、`bash "$SKILL/scripts/pj-open.sh" <正relpath> --query "<原文>" --prompt-file <ファイル>` を実行する。`--query` で原文が正しい行き先に記録され、振り分けの1行は付け直される
2. 誤った行き先の記録を消す：`python3 "$SKILL/scripts/pj-learn.py" forget "<原文>" <誤relpath>`（記録が無ければ何もしない）
3. 下の「恒久的な是正」を行う
4. このセッションの作業場は自分で閉じない。まだ何も書いていなければ閉じてよいこと、書いたものがあれば先にコミットすることを伝える

## 恒久的な是正

誤起動が1件でも起きたら、その場で根治まで実施する。**ユーザーへの確認・承認は取らない**（2026-08-31 決定。承認待ちにすると是正が積み残され、同じ語で誤起動が繰り返される）。提案として差し出さず、実施した結果を報告する：

- 対象プロジェクトの `CLAUDE.md` 先頭 frontmatter の `aliases` に、ヒットさせたい語を追加する。
- **`aliases` だけで終えず、「切り分け／使い分け」節も足す。** aliases は「引き寄せる」だけで「取り違えを防ぐ」働きはない。紛らわしい近傍プロジェクトの側に「この話題の正本は `<正しいプロジェクト>`」という除外・参照文を書くこと（索引では `boundary` として抽出され、CANDIDATES の理由表示と判断材料になる）。`boundary` は似たプロジェクトの取り違えを防ぐ唯一の記述だが記入率が低いため、**誤起動を1件直すたびに1件埋める**。
- **切り分け節は見出しの語で判定される。** 索引が `boundary` として拾うのは、見出しに `切り分け`・`使い分け`・`scope`・`何を置`・`境界` のいずれかを含む節だけ（`pj-recommend.py` の `BOUNDARY_HEADS`）。「○○の管理先」「○○の扱い」のような見出しで正本の所在を書いても索引には入らず、書いたのに効かない状態になる（2026-08-31 の実例：あるプロジェクトに別のプロジェクトへ回す記述はあったが、見出しが「管理先」だったため索引に入らず誤起動した）。既存節へ書き足すときは、見出しに上記の語が入っているかを先に確かめる。
- 編集後に `python3 "$SKILL/scripts/pj-recommend.py" index --rebuild` で索引を再構築する。
- **再構築後に `python3 "$SKILL/scripts/pj-router.py" route "<誤起動したときの原文クエリ>"` を実行し、判定が直ったことを確かめてから報告する。** `DIRECT<TAB><正relpath>` になっていれば根治。CATALOG のままなら aliases の語がクエリ文にそのまま含まれていない。あわせて、引き寄せてしまった側の代表クエリも流し、そちらが従来どおり当たること（回帰していないこと）を確認する。

## 注意

- `<relpath>` は必ず `pj-go.sh` の出力（CANDIDATES/CATALOG）に実在する `path` を一字一句そのまま使う。創作・改変しない。
- 索引に無いプロジェクトは開けない（`CLAUDE.md` が索引の要件）。`CATALOG` に見当たらないのに存在するはずだとユーザーが言う場合、そのフォルダに `CLAUDE.md` が無い可能性を伝える。
- `pj-open.sh` は Orca が動いていれば Orca の作業場で、動いていなければ iTerm2（`osascript` で新規ウィンドウを作る）で開く。どちらも無い端末では開かない。
- 機密プロジェクト（frontmatter `confidential: true`）を候補提示する際も、`purpose`/`boundary` の要約以上の内容はチャットに展開しない。

## worktree

同じリポジトリで claude を2つ動かすと git のインデックスを共有し、片方の `git add` にもう片方の変更が混ざる。そのため iTerm2 で開くときは、そのリポジトリの本体で claude が動いていなければ本体で、動いていれば `.claude/worktrees/<名前>/`（ブランチ `wt/<名前>`）に worktree を作って開く（`pj-worktree.sh`）。Orca は作業場ごとに worktree を作る。

worktree で始めたセッションは、終えるときに `bash "$SKILL/scripts/wt-finish.sh"` で既定ブランチへ統合し、worktree とブランチを片付ける（未コミットがあれば止まる。`--dry-run` で先に見られる）。セッション終了の手順（`guides/SESSION-END.md`「worktree セッション」）がこれを呼ぶ。中身の無いまま残った `.claude/worktrees/` の worktree は、次に pj で開くときに回収される。
