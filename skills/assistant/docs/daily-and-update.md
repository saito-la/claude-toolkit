# 朝の一式と日中の更新

作成日：2026-10-18
改訂日：2026-11-08

## 1. 呼び方と前提

### 1.1. 呼び方

インスタンスのセッションの中で「init」と言えば朝の作業を、「update」と言えば日中の today.md の作り直しを、承認を挟まずに通す仕組みの仕様（2026-10-18 決定）。各作業の中身の決まりは `design.md` の各節が正本で、ここは呼び方・順番・速さとトークンのための作り・前日分の移送を持つ。

- 「init」「update」「updateして」は、エンジンのスキル `assistant`（[../SKILL.md](../SKILL.md)）が受ける。スキルはこの文書を読んで手順どおりに進めることだけを持つ
- 効くのはインスタンスのフォルダ（`assistant.json` のあるフォルダ）のセッションの中だけ。ほかのフォルダでは何もしない
- Claude Code の組み込みの `/init` とは別物。スラッシュを付けずに「init」と言う

### 1.2. スクリプトの呼び方

スクリプトはエンジンの `scripts/` にある。エンジンの場所は `~/.claude/skills/assistant`（claude-toolkit の `install.py` が置く。`../README.md`「導入」）で、以下では `<エンジン>` と書く。

- インスタンスのフォルダを作業ディレクトリにして `node <エンジン>/scripts/<名前>.mjs` で呼ぶ。スクリプトは作業ディレクトリから上へたどって `assistant.json` のあるフォルダをインスタンスとみなす
- 出力（`data/`・today.md の点検の控え）はインスタンスのフォルダに書く。エンジンのフォルダには何も書かない
- 設定で使わないことにした機能（`features`）のスクリプトは、呼ばれても何もせずに終わる。手順は使い手ごとに分けず、下の各段の「設定が true のときだけ」を飛ばす

## 2. 速さとトークンのための作り

### 2.1. 重さを決めるもの

道具を1回呼ぶたびに、それまでの文脈を全部読み直す。重さを決めるのは、文脈の大きさと往復の回数の積である。確かめる件数そのものではない。そこで 2.2〜2.5 の4つを置く（2026-10-18 決定）。

### 2.2. 新しいセッションで行う

設定の `features.sessions` が true なら、最初に設定の `sessions.command`（以下 `<sessions>`）で `<sessions> ctx` を流し、文脈の大きさを測る。10 万トークンを超えていたら（終了コード 2）、何もせずに `/clear` してから言い直すよう伝えて止まる。2026-10-18 に測った値は、長く続いたセッションで約 30 万、新しいセッションで 3〜4 万だった。`features.sessions` が false なら測らず、長く続いたセッションなら `/clear` してから言い直すよう伝える。

### 2.3. 機械で決められる確かめはスクリプトで済ませる

`evidence.mjs` が、前回の today.md の各項目について、前回より後に起きたことを1回で集め、印を付ける。前回は today.md を git に入れるインスタンスでは前回の commit、入れないインスタンスでは today.md を最後に書いた時刻。ただし項目が参照する台帳の行を最後に書いた時刻（git blame）が前回より前なら、その時刻から見る。印は 閉じた・ずれた・送った・予約した・下書き・届いた・鍵なし・変化なし の8つ。

- 起点を台帳の行に合わせるのは、載せた時点で既に済んでいた項目を拾うため。前回からの差分だけでは、そういう項目は毎回「変化なし」になり、載り続ける。2026-11-08、11/4 08:31 に受信メールから足された台帳の行に、08:38 の返信と 08:49 の続報があったのに、4日間「変化なし」で載り、開いた先のセッションで済んでいたと分かった。台帳の行を直せば起点も進んで印は消えるので、この印は「台帳を直す」合図でもある
- 「鍵なし」は Gmail の ID もアドレスも持たない項目（台帳の行だけの項目を含む）。送受信を機械で確かめられないので、「変化なし」と同じ扱いにしない送ったか・予約か・下書きか・届いたかの判定は `scripts/lib/gmail-kind.mjs` が正本で、`check-today.mjs` も同じ判定を使う。

- update では「変化なし」「鍵なし」の項目は開かずにそのまま載せてよい（その日の init で確かめ済みのため）。init ではすべての項目を確かめる（2.4）
- 「下書き」は Gmail の未送信の下書きで、完了の証拠にならない。項目が送ることを求めていて、付いた印が「下書き」だけなら、まだ送っていないものとして載せる（2026-10-29、未送信の下書きを「送った」と判定し、送っていない連絡を済んだと読みかけた）
- それ以外の項目だけを読む
- 見る範囲と見られないもの（スレッドの外の送信など）はスクリプトの冒頭に書いてある
- その端末で初めて回すとき（today.md がまだ無い）は前回が無いので、すべての候補を「1件ずつの完了確認」で確かめる

2026-10-18 の朝は 67 項目中 64 が変化なしで、約 11 秒だった。前回の today.md に無いもの（新しく届いたメール、新しい期限超過、作業用の文書の当日の欄、作業ログの無いセッション）は、今までどおり `data/candidates.json` と `<sessions> gaps`（`features.sessions`）から拾う。

### 2.4. 項目の確かめは Sonnet のサブエージェントに並列で分ける

init では、載せる候補のすべて（印に関わらず）を、プロジェクトごとにまとめて Sonnet のサブエージェントへ並列に渡す（2026-11-08 決定）。前回からの差分だけで判断して済んだ項目を載せ、開いた先のセッションで済んでいたと分かるほうが、使い手の時間を無駄にするためである。update では、印が「変化なし」「鍵なし」以外の項目が 8 件を超えたら同じように分ける。どちらも1件ごとには分けない。1本あたり1〜2万トークンの立ち上げの費用がかかるためである。

- 渡すもの：項目の本文、台帳のパスと行、`evidence.mjs` の notes。サブエージェントは台帳の行・関連メールのスレッド（台帳の行を書いた時刻より後）・予定表を引き、台帳の行が今の状態を言い当てているかを確かめる

- サブエージェントは読むだけで、台帳・メール・作業用の文書を書き換えない
- 返すのは、1項目1行の「項目／判定（済んだ・状態が変わった・変化なし）／根拠のメッセージ ID か台帳の行／次の一手」だけ
- 人名の漢字は根拠の本文から写させ、推測させない

### 2.5. まとめるのは本体

本体が受け持つのは次の作業である。

- 台帳を閉じる・直す（`design.md`「書き込み方針」）
- 項目どうしを見比べる（台帳どうしの食い違い、予定表の時刻が依頼と逆になっている、など）
- 優先順を決め、today.md を書く

項目を横に見比べて初めて分かる食い違いは、1件ずつ切り離したサブエージェントには見えないためである。

## 3. 時間とトークンの記録

設定の `features.sessions` が true のときだけ行う。最初に `date -Iseconds` で時刻を控える。最後に `<sessions> cost --since <その時刻> --label init|update --log data/run-costs.csv` を流し、結果を報告の1行目に書く。CSV は手順を削るかどうかの判断の材料にする。jsonl では1つの応答が複数行に記録されるので、応答ごとに1回だけ数える（道具の README）。

## 4. init の手順

順番に意味がある。

- Done を作業用の文書に書いてから記録用の文書へ移すので、Done も記録用の文書に残る
- today.md を作ってから作業用の文書の前日分を消すので、前日の欄に書かれた項目を拾い落とさない

1. 文脈の大きさを測り（2.2）、時刻を控える（3）
2. 設定の `features.done` が true なら、前日のやったことを作業用の文書へ書く。決まりは `design.md`「やったことの記録」
   - 主な材料は git のコミットと作業ログ。作業ログの無いセッションと使った機だけを `<sessions> gaps --date <前日>` で拾う。jsonl を直に読まない
   - 書くのは `doc-done.mjs --heading "<前日の見出し>"`。dry-run を見てから `--apply`
3. today.md を作る
   - 材料：`evidence.mjs`（2.3）と `data/candidates.json`。セッションの途中なら先に `collect.mjs` を流し直す
   - すべての候補を Sonnet のサブエージェントで確かめる（2.4）。確かめ方は `design.md`「1件ずつの完了確認」「期限の扱い」。インスタンスの `overview.md` にある使い手固有の決まりも当てる
   - 済んだ行は `close-items.mjs --apply` で閉じる
   - 「やること」は `candidates.json` の `capacity` に収まる量だけにし、各項目に見積を書く（`design.md`「業務量」）。インスタンスに `keep-in-mind.md` があれば、その直下に「意識しておく案件」を優先順で置く（`design.md`「意識しておく案件」）
   - `attendanceNotices` に連絡が済んでいない日があれば「やること」に出す（`design.md`「勤務先への連絡」）
   - 書き方は `design.md`「出力」の印 → linkify（`features.pjLinks`）→ 点検（`check-today.mjs`、`features.checkNames` なら `check-names.mjs` も）
   - 通ったら、today.md を git に入れるインスタンスでは today.md だけを commit・push する
4. 作業用の文書の前日分を記録用の文書へ移す（5）
5. 締切をタスクに載せ（`deadline-tasks.mjs --apply`。`deadlineTasks.credential` があるとき）、2w 予定を更新する（`doc-2w.mjs --apply`）。順はこのとおりで、2w は載せたタスクを各日の先頭に入れる
6. 時間とトークンを出し（3）、today.md を開いて報告する（Mac は `open today.md`）
   - 報告に書くもの：閉じた台帳の行と根拠、記録用の文書へ移した日と行数、足した・完了にした締切のタスク、2w に足した行数、点検の結果、止まった手順の理由
   - today.md の中身は繰り返さない

## 5. 作業用の文書の前日分を記録用の文書へ移す

作業用の文書の前日以前の日付見出しの欄を、記録用の文書（設定の `logDoc`）の先頭へ写し、作業用の文書から消す。それまで使い手が毎朝手で移していた（2026-09-20 確認）のを、仕組みが受け持つ。実体は `../scripts/doc-log.mjs`。

- 移す範囲は、日付見出しと、その直下の最初のかたまり（空行までの連続した行）
  - その日の予定と、`doc-done.mjs` がその直後に足す Done@ ブロックがここに入る
  - かたまりの後ろにある日付の無いメモは移さない。見出しが消えると、上の新しい日の欄に入る
  - 使い手が手で移していた 2026-10-16 分までの形に合わせた
- 記録用の文書の書き方
  - 新しい日付を先頭に置く。日の区切りは空行1つ
  - 日付の行も本文の書式にする。太字・斜体・下線・色・リンクは外す（2026-10-18 決定）
- 消すときの確かめと承認
  - 写した後に記録用の文書を読み戻して一致を確かめ、作業用の文書を読み直して消す範囲が変わっていないことを確かめてから消す
  - この2つが揃えば承認を取らずに消す（2026-10-18 決定。`design.md`「書き込み方針」の、作業用の文書から消すときの承認の例外）
  - どちらかが合わなければ、作業用の文書は消さずに止まる
- Done@ の行がかたまりの外にある日は、どこまで移すか決められないので止まる

## 6. update の手順

1. 文脈の大きさを測り（2.2）、時刻を控える（3）
2. `collect.mjs` と `evidence.mjs` を流す。項目が触れるリポジトリは先に `git fetch` する
3. 新しく起きたことを見る：`candidates.json` の新着メールと返事、督促が要る待ち（`reminders`。`design.md`「督促の扱い」）、勤務先への連絡が済んでいない日（`attendanceNotices`。`design.md`「勤務先への連絡」）、`<sessions> gaps --date <今日>`（`features.sessions`）、作業用の文書の当日の欄
4. 読む必要のある項目を確かめ（2.4）、台帳を閉じる・直す
   - ほかのセッションの未コミットの変更がある台帳には触らず、報告に書く
5. today.md を書き直す
   - 済んだ項目を外し、ボールが戻ってきた件を「やること」へ上げ、新しいものを足す。書き方は `design.md`「今日の一覧の書き方」（箇条書き・1 action 80文字以内・受け身の案件は載せず、他人ボールは督促が action になるものだけ）
   - 残り時間に合わせて「今日の予定」と並びを考え直す
   - 使い手が手で足した節はそのまま残す
   - 行番号が動くので、書く前に `data/today-refs.json` の当日の控えを空にする
   - そのあとは init の 3 と同じ書き方・点検・commit・push
6. 時間とトークンを出し（3）、today.md を開いて報告する
   - 報告に書くのは変わったところだけ：外した項目と根拠、上げた項目、閉じた・直した台帳の行、触らなかった台帳
