# SAS

作成日：2026-08-22
改訂日：2026-08-23

SAS を扱うときの共通の作法。`~/.claude/SAS-local.md` があれば併せて読む（無ければスキップ）。どの端末からどう実行するか、ログがどこに出るかはそちらにある。

## 実行できるかを推測で答えない

SAS に macOS ネイティブ版は無い。したがって Mac で `which sas` が空なのは当たり前で、それは「この環境で SAS を実行できない」ことの証明にならない。リモート実行の経路が張ってあることがある。

可否を答える前に次の順で調べる。ローカルだけ見て「使えません」と答えない。

1. `~/.claude/SAS-local.md` を読む
2. そこが指す環境文書と端末別の記録を読む
3. ラッパーの有無を見る（`command -v` で PATH を確認する）
4. 実行先への疎通を確かめる

逆に、コードを直しただけの状態を「通った」と報告しない。SAS が動く端末で回すまで検証は完了していない。

## 文字符号化

`.sas` は UTF-8（BOM なし）で保存する。ただし日本語版 SAS の既定の config は shift-jis で、`.sas` も出力もログも CP932 になる。UTF-8 で運用するには起動時に UTF-8 用の config を `-config` で明示する（配置は `nls\u8\sasv9.cfg`）。

CP932 セッションに UTF-8 の `.sas` を投げると、日本語の末尾バイトが直後の `;` を飲んでマクロ定義が壊れる。症状は遠くの行の構文エラーとして出るので原因が見えにくい。日本語をコメントではなく実行行に書いているときに踏みやすい。`.sas` の符号化とセッションの符号化は必ず揃える。

逆向きの落とし穴もある。`proc export` はセッションの符号化で書くため、UTF-8 セッションでなければ他言語（R・Python）が読めないファイルが出る。層をまたいで受け渡すファイルは符号化を揃える。

## バッチ起動

`sas.exe` は GUI サブシステムのアプリで、起動すると即座に制御を返す。呼び出し側で明示的に待たないと、前の段が書き終える前のファイルを次の段が読む。PowerShell なら `Start-Process -Wait` を使う。

PowerShell から引数を渡すときは1本の文字列にする。配列で渡すと `-initstmt "%let lang=en;"` のような空白を含む値が分割されて起動に失敗する。

`autoexec.sas` はカレントディレクトリから探される。`-sysin` に絶対パスを与えても、カレントが違えば読まれない。バッチでは SAS 起動の前にプロジェクトのルートへ移動する。読まれなかったことは「マクロ変数が未解決」という形で後から現れるので、libname やパスが解決していないときはまず autoexec が読まれたかを疑う。

## 成否の判定

終了コードで判定しない。SAS は多くの失敗を 0 で返す。判定はログの行頭で行う。

- `^ERROR` と `^WARNING` の件数を数える。行の途中に現れる ERROR という語は数えない
- ログはセッションの符号化で書かれる。読む側の符号化を合わせないと検出が効かない。shift-jis セッションのログを UTF-8 で読むと ERROR を取りこぼす。CP932 のログは `iconv -f SHIFT-JIS -t UTF-8` を通してから読む
- WARNING は残ってよい。既知の WARNING と新しい WARNING を区別して報告する

判定を人が目で読む運用にしない。段が増えると見落とすので、ログを機械的に走査して件数で止める形にする。

ログのファイル名に段と日付だけを使うと、同じ日に複数の端末やセッションから同じ段を回したときに上書きされ、どちらの記録か分からなくなる。実行元を名前に含めるか、同じ対象を同時に複数から回さない運用で避ける。

## 書き方で踏みやすいもの

オープンコードの `%if-%then` には `%do;…%end;` が要る。無いと `%DOが必要ですが、見つかりません。` で以降が丸ごとスキップされ、実行されていないのに ERROR が1件だけ出る形になる。

`proc sql` は再マージで行を重複させる。集計列の別名を `order by` に置くこと自体が引き金になる。値だけを突合すると、行が重複していても値が同じなので一致してしまう。突合では行数も併せて見る。対処は `nodupkey` 等で明示的に落とすこと。

`proc format cntlin=` は同じ `FMTNAME` が連続していることを前提にする。複数の書式の行が混在した入力を渡すと、黙って一部だけが登録される。

## 他言語と結果を突き合わせるとき

同じ統計量でも既定が処理系で違う。突合するなら既定を明示して揃える。実際に食い違う代表例は次のとおり。

- 四分位点の定義（SAS の `QNTLDEF`。R の `quantile(type=)` と対応させる）
- 生存関数の信頼区間の型（SAS の `CONFTYPE`。R の `survfit(conf.type=)` と対応させる）
- 丸め。SAS の `w.d` は絶対値の大きい側へ丸め、C ライブラリの丸め（R の `formatC`・`sprintf`）は二進表現に従う。4.45 が 4.5 と 4.4 に分かれる
- 行の並び。照合順序はロケール依存で、記号と大小文字の扱いが処理系で違う。バイト順に揃えたいなら双方でそれを明示する（R なら `sort(method="radix")`）

数値の許容差は相対 1e-8 程度から始め、合わなければ緩める。緩めたときはその値と理由を記録する。例数・分母・イベント数のような整数は許容差を置かず完全一致を求める。ここが合わないのは丸めではなく、対象集団の絞り込みかデータの扱いが違っている。

## 実行の前後

実行前にリポジトリを `git pull` する。生成物は git 管理外で、正本はリポジトリ側のスクリプトにある。古い版で回すと他の端末が入れた改善を黙って巻き戻す。

生データ・ログ・出力を git にコミットしない（`.sas7bdat`・`.sas7bcat`・`.xpt`・`.sav`・`.dta`・`.log`・`.lst`・`.csv`・`.rtf`・`.xlsx` 等）。データの正本は別に置き、リポジトリはコードと手順だけを持つ。

`.xpt`（XPORT v5）は文字 200 バイト・変数名 8 文字の制限があり、長い自由記述を入れると黙って切れる。長い文字列を含むデータの受け渡しには使わない。

## クラウドストレージ上のデータを読むとき

オンデマンド取得のクラウドストレージ（Box Drive・OneDrive 等）をマウントしたフォルダを libname で指すと、初回アクセスだけ取得が間に合わず失敗することがある（Windows では `Windows error code 1006` から `ライブラリは無効です` へ連鎖する）。一過性なので、同じ処理を1回リトライする作りにしておく。リトライは転送層ではなく SAS の起動層の責務に置く。

同じ理由で、書き込み直後のファイルを次の段が読むときは書き込みが落ち着くまで待つ。端末をまたぐ同期には数十秒かかるので、別の端末が書いたものを突合の入力にするなら揃うまで始めない。

## 報告

実行結果を報告するときは、段ごとの ERROR 件数・WARNING 件数・所要時間と、成果物の実体（パスとサイズ）を添える。「成功しました」だけで終えない。

ERROR が出たときは、ログの ERROR 行と、それがどのログファイルのものかを示す。
