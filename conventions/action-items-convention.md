# action-items.md 規約

作成日：2026-05-31
改訂日：2026-08-11

## 概要

複数セッションにまたがる進行中プロジェクトにおいて、積み残しアクションを一元管理するための規約。セッション開始時に即座に状況を把握できるようにする。

## 背景・動機

- 次回アクションが各 `docs/*-work-log.md` に分散しており、セッション開始時に拾いにくい
- work-log は時系列記録であり、「現在有効なアクション」の把握には向かない
- 設計文書・手順書にもアクションが埋め込まれており探索コストが高い

## 規約

### 導入の判定

**判定は自動で行い、ユーザーに確認しない。** 既に `action-items.md` があるなら更新するだけで、判定は要らない。

無いプロジェクトで新規に作るのは、次の2つを**ともに**満たすときだけ。

- 次のセッション以降に持ち越す未完了の行動が1件以上残っている（相手待ち・依頼中・条件付き実行を含む）
- その行動が git log・コード・既存 `docs/` から自明に復元できない

どちらかを欠くなら作らない。単発タスク中心のプロジェクト、コードベース中心で状態が git log から自明なプロジェクトが該当し、次回アクションは work-log に書いて終える。

### ファイル配置・命名

配置と命名はここが正本（`SESSION-END.md` はここを参照する）。

- `<project-root>/action-items.md` — プロジェクトルート
- `<project-root>/<サブプロジェクト>/action-items.md` — サブプロジェクト・個別案件を抱えるなら、その直下にも置いて親と分ける
- `action-items-archive.md` — 完了項目の退避先。live ファイルと同じディレクトリに置く

同一ディレクトリ内で対象（企業・人物など）ごとに分ける必要があるときだけ `<topic>_action_items.md`（人物なら `<slug>_action_items.md`）を使う。

### ファイル形式

行動の行以外に置いてよいのは、**タイトル・日付2行・節見出し・節頭の参照1行**だけ。それ以外の地の文を置かない。

- **プロジェクトの説明・スコープ・他ファイルとの切り分けを書かない** — `CLAUDE.md` が正本で、セッション開始時に必ず読まれる
- **規約へのリンクを書かない** — グローバル指示から常時読まれるので、ファイルごとに書く意味がない
- **`action-items-archive.md` へのリンクを書かない** — 同じディレクトリの固定名だと規約が決めている
- **「達成済」「現状」等の状態ブロックを書かない** — 済んだことは archive と git log が持つ

**節頭の参照1行は、その節の2行以上が同じ背景文書を共有するときだけ置く。** 1行しか使わない文書へのリンクは、その行の中に埋める。書き方は `正本：<リンク>` の1行（日付行と同じラベル形式に揃える）。

```markdown
# <プロジェクト名> Action Items

作成日：YYYY-MM-DD
改訂日：YYYY-MM-DD

## 直近

- [ ] **重要度高いもの**（太字推奨）
- [ ] 通常のアクション

## 中期

- [ ] 着手時期が先の行動

## 保留・継続検討

- [!] 判断待ち・ブロック中の行動
```

`[ ]` と `[!]` の使い分けは下記「記載できるのは未解決のactionableな事項のみ」が正本。

節の見出しは名詞句のみとし、**括弧書きで期限を補わない**（`## 直近（6月上旬まで）` は不可）。「直近」「中期」のような相対区分に月名を混ぜると、月をまたいだ瞬間に見出しが嘘になる。**外部で日付が固定されている案件**（学会・季節作業など）に限り、`## 7月末まで` `## 9月以降` のように月名そのものを見出しにしてよい。

### 対象別の分離

**プロジェクトが複数の対象（端末・サイト・アカウント・環境など）を持つ場合、「全対象に共通の事項」と「特定の対象に固有の事項」を上位の節で明確に分ける。** 混在させると、ある対象の前に座ったときに自分に関係する行を毎回選り分けることになり、選り分けを間違えれば作業が漏れる。

- 共通側には、対象を選ばない作業・方針・判断待ちを置く。
- 固有側は対象ごとに節を立て、その対象でしか起きない作業だけを置く。
- **「全対象で1回ずつ実行する作業」は共通側に1行だけ書き、その行に残っている対象名を列挙する。** 対象ごとの節に同じ作業を書き写さない（同じ事実を2箇所に書かないため）。

### 並べ方

**節の並びも、節の中の行の並びも、優先順位順にする。** 発生順・話題順に積むと、上から読んでも何から手を付けるかが分からない。優先順位が同じものだけを発生順に並べる。

### 記載できるのは未解決のactionableな事項のみ

**action-items.md に書けるのは「未解決で、かつ実行できる行動」だけ。情報・注意事項・状態の記述は書かない。** 例外を作らず徹底する。

書いてよいもの：

- `- [ ]` 実行内容が確定していて、着手できる行動
- `- [!]` 判断待ち・ブロック中の行動。**ただし「誰の何の判断を待っているか」と「その判断が出たら何をするか」が書かれていること。** 待つ理由だけを書いた行は情報であり対象外

書かないもの（見つけたら移動先を決めて排除する）：

- 仕様・設計・方針の説明 → `overview.md` 等の生きた文書
- 現状の状態・観察・注意事項（「〜になっている」「〜に注意」「様子を見る」） → 該当する設計文書。移動先が無ければ削除
- 手順書・コマンド一式・判定フロー → `docs/` 配下
- 決定事項の背景説明・確定した前提の一覧 → `docs/` 配下
- 過去に実行したプロンプトの全文 → 削除（再利用価値が無い）
- 既に他の文書が正本を持っている事実の再掲 → 削除して参照1行に置き換える
- **「運用しながら育てる」「必要になったら考える」類の常設メモ** → 設計文書の該当箇所へ。着手条件の無いものは行動ではない

判断の目安は「この行を読んで、今すぐ次の一手が決まるか」。決まらない記述は資料であり、置き場は `docs/` か設計文書になる。**移動先が無く、消しても失われる判断が無いものは削除する**（無駄な整理より先に廃止・削除を検討する）。

既存ファイルを開いたときは、この基準で1度掃除してから作業に入る。掃除で消した情報のうち残す価値があるものは、移動先を明示して報告する。

### CLAUDE.md への参照追加

プロジェクトの `CLAUDE.md` 先頭付近に以下を追記：

```markdown
## セッション開始時

**まず `action-items.md` を読んで現在の積み残しを把握してから作業を始めること。**
```

### 完了項目のアーカイブ

`[x]` を live のファイルに溜めない。同じディレクトリの `action-items-archive.md` へ退避し、`action-items.md` には未完了だけを残す。

削除ではなく退避にする理由は、完了項目に「なぜそうしなかったか」の判断根拠が書かれることがあり、work-log は日付でしか辿れないため。手で消すと判断根拠ごと消える。

退避は機械的に行う。判断は要らない。

```bash
python3 ~/.claude/scripts/archive-action-items.py $(find . -maxdepth 2 -name action-items.md)
```

- `- [x]` ブロック（続くより深いインデント行を含む）を移す
- 未完了 `- [ ]` を配下に持つ親は、まだ終わっていないので残す
- 未完了が残らないセクションは見出し・地の文ごと移る
- archive 側に同名セクションがあればその末尾へ追記する
- 冪等。`--dry-run` で事前確認できる

退避を溜めると効かなくなる。制定から3か月間これを行わなかったリポジトリでは、初回適用時に完了73件・31KB を退避し、`action-items.md` が 55KB → 19KB になった。

**完了した節を archive へ移すときは、結果の要点と正本へのリンクに要約する。** 実施結果の詳細を持つ文書が別にあるなら（作業ログ・対象ごとの記録など）、archive はそこを指すだけでよい。当日貼ったプロンプトの全文のように再利用価値の無いものは落とす。

## 運用ルール

- セッション終了時の更新・退避の実行は `~/.claude/SESSION-END.md` の Step 2b が正本
- work-log には引き続き詳細な文脈を残す。action-items.md は**ポインタ**、詳細は各 docs へ
- **1つのプロジェクトの action-items が長くなりすぎたら、領域ごとにサブプロジェクトへ分ける**。ファイルを分ける前に、その領域が独立したセッションを立てるべき単位かを疑う
