# action-items.md 規約

随時更新（2026-08-10 時点。制定 2026-05-31）

## 概要

複数セッションにまたがる進行中プロジェクトにおいて、積み残しアクションを一元管理するための規約。セッション開始時に即座に状況を把握できるようにする。

## 背景・動機

- 次回アクションが各 `docs/*-work-log.md` に分散しており、セッション開始時に拾いにくい
- work-log は時系列記録であり、「現在有効なアクション」の把握には向かない
- step系ドキュメント（step7, step8等）にもアクションが埋め込まれており探索コストが高い

## 規約

### 対象プロジェクト

**導入すべきプロジェクト**の条件（いずれか該当）：
- 複数セッションにまたがる戦略的な進行中プロジェクト
- 積み残しの追跡が重要なもの（面談待ち・依頼中・条件付き実行など）

**導入不要**：
- 単発タスク中心のプロジェクト
- コードベース中心でgit logから状態が自明なプロジェクト

### ファイル配置

```
<project-root>/action-items.md   # プロジェクトルートに配置
```

### ファイル形式

```markdown
# <プロジェクト名> Action Items

> このファイルはセッション開始時の状況把握用。完了したら `[x]` に変更し、不要になったら削除する。
> 詳細な背景は各 `docs/stepN_*.md` および `docs/*-work-log.md` を参照。

最終更新: YYYY-MM-DD

---

## 直近（目安: 〜X月末）

- [ ] **重要度高いもの**（太字推奨）
- [ ] 通常のアクション

## X月以降

- [ ] 中期アクション

## 保留・継続検討

- [ ] 条件が揃うまで動かせないもの
- 箇条書き（チェックボックスなし）で継続観察中の事項
```

### 更新日表記

**`最終更新: YYYY-MM-DD` を文書冒頭に1行置く。** 生きた文書の「随時更新（YYYY-MM-DD 時点）」は使わない（→ [[20260619-living-doc-structure]]）。**`action-items.md` の更新日表記はこの節が正本**で、他の規約が別表記を指示していてもこちらを優先する。

日付の後ろに改訂回数や反映内容を括弧書きで足さない。何が変わったかは行そのものと git log が持つ。

### 対象別の分離

**プロジェクトが複数の対象（端末・サイト・アカウント・環境など）を持つ場合、「全対象に共通の事項」と「特定の対象に固有の事項」を上位の節で明確に分ける。** 混在させると、ある対象の前に座ったときに自分に関係する行を毎回選り分けることになり、選り分けを間違えれば作業が漏れる。

- 共通側には、対象を選ばない作業・方針・判断待ちを置く。
- 固有側は対象ごとに節を立て、その対象でしか起きない作業だけを置く。
- **「全対象で1回ずつ実行する作業」は共通側に1行だけ書き、その行に残っている対象名を列挙する。** 対象ごとの節に同じ作業を書き写さない（同じ事実を2箇所に書かないため）。

### 並べ方

**節の並びも、節の中の行の並びも、優先順位順にする。** 発生順・話題順に積むと、上から読んでも何から手を付けるかが分からない。優先順位が同じものだけを発生順に並べる。

### 本文に置かないもの

**action-items.md はポインタであって資料ではない。** 次のものは本文に書かず、`docs/` 配下の該当文書へ置いて1行の参照だけを残す。

- 手順書・コマンド一式・判定フロー
- 決定事項の背景説明・確定した前提の一覧
- 過去に実行したプロンプトの全文
- 既に他の文書が正本を持っている事実の再掲

判断の目安は「この行を読んで次に何をするかが決まるか」。決まらない記述は資料であり、置き場は `docs/` になる。

### CLAUDE.md への参照追加

プロジェクトの `CLAUDE.md` 先頭付近に以下を追記：

```markdown
## セッション開始時

**まず `action-items.md` を読んで現在の積み残しを把握してから作業を始めること。**
```

### セッション終了ルーチンでの扱い

正本は `~/.claude/SESSION-END.md` の Step 2b。要点は次のとおり。

- プロジェクトルート（およびサブプロジェクト直下）に `action-items.md` が存在する場合のみ実行
- 当セッションで完了したアクションを `[x]` に変更
- 当セッションで発生した新規アクションを追記
- 完了項目を `action-items-archive.md` へ退避する（下記「完了項目のアーカイブ」）
- 存在しない場合はスキップ（新規作成の義務はない）

### 完了項目のアーカイブ

`[x]` を live のファイルに溜めない。同じディレクトリの `action-items-archive.md` へ退避し、`action-items.md` には未完了だけを残す。

削除ではなく退避にする理由は、完了項目に「なぜそうしなかったか」の判断根拠が書かれることがあり、work-log は日付でしか辿れないため。手で消すと判断根拠ごと消える。

退避は機械的に行う。判断は要らない。

```bash
python3 ~/.claude/scripts/archive-action-items.py $(find . -maxdepth 2 -name action-items.md)
```

- `- [x]` ブロック（続くより深いインデント行を含む）を移す
- 未完了 `- [ ]` を配下に持つ親は、まだ終わっていないので残す
- 未完了が残らないセクションは見出し・地の文ごと移る
- archive 側に同名セクションがあればその末尾へ追記する
- 冪等。`--dry-run` で事前確認できる

**実績**: あるリポジトリでの初回適用時、完了73件・31KB を退避し、`action-items.md` は 55KB → 19KB になった（規約制定から3か月間、この掃除が一度も行われていなかった）。

## 運用ルール

- `[x]` にしたアイテムは溜めず、セッション終了ごとに `action-items-archive.md` へ退避する（上記「完了項目のアーカイブ」）
- **完了した節を archive へ移すときは、結果の要点と正本へのリンクに要約する。** 実施結果の詳細を持つ文書が別にあるなら（作業ログ・対象ごとの記録など）、archive はそこを指すだけでよい。当日貼ったプロンプトの全文のように再利用価値の無いものは落とす
- work-log には引き続き詳細な文脈を残す。action-items.mdは**ポインタ**、詳細は各docsへ
- `SESSION-END.md` の Step 2b で action-items.md を更新する（`~/.claude/SESSION-END.md`）
- **1つのプロジェクトの action-items が長くなりすぎたら、領域ごとにサブプロジェクトへ分ける**。ファイルを分ける前に、その領域が独立したセッションを立てるべき単位かを疑う
