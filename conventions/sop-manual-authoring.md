# 手順書・マニュアル作成規約

作成日：2026-07-03　改訂日：2026-08-01

## 概要

全プロジェクト共通。SOP・手順書・業務マニュアルを作成するときの標準的な構成と記述作法を定める。実際の手順書作成時にレビューで指摘・修正された点を、再現可能な作成方法として一般化したもの。

手順書は「誰が何をするか」に徹する文書であり、案件の全体像を随時更新する「生きた文書」（`overview.md` 等、[[living-doc-structure]]）とは文書型が異なる。日付表記は全文書共通で、文書型による違いはない。

## 背景と動機

- 手順書に制度・背景の解説や注意事項を混ぜると、肝心の「手順」が埋もれ、実務者が追えない。
- 主語のない動作記述は、誰の責任か曖昧になり、属人化・抜けを生む。
- 版管理・改訂履歴・承認ワークフローを文書内に抱えると煩雑化し、最終形の一読性が落ちる（ISO文書管理でいう「最終形＝単一の真実」を重視）。
- 対外的な依頼などは、相手の格に応じた発信主体でなければ非礼・不整合になる。
- 太字・斜体・下線などの文字修飾は、公的様式では避けるのが通例で、多用は可読性をむしろ下げる。

## 適用対象

- SOP・手順書・業務マニュアル（定常業務の作業手順を定める文書）。
- 対象外：案件の生きた文書（`overview.md` 等）、単発メモ、議事録・調査の凍結記録。

## 標準構成

セクションは次の並びを標準とし、各セクションの役割を固定してオーバーラップさせない。

1. 目的
2. 適用範囲
3. 役割と責任
4. 手順（段階は `4.1.` 以下の小見出しに配置）
5. 付録（テンプレート・文例）

制度・背景の解説セクション（「○○の要点」等）は置かない。必要なら別文書（概念ノート・wiki）へ分離し、手順書からは参照にとどめる。

## セクション別の規約

- 目的：この文書が何を定めるかを1文で簡潔に述べる。ねらいの列挙・注意事項・背景は書かない（それらは別セクションまたは別文書）。
- 適用範囲：対象（誰から・どの経路・どの類型）を明示する。
- 役割と責任：登場する役割を短い代名詞（ラベル）で定義する。例：相談室／事務局／担当部署／レビュアー／責任者。この節が役割定義の唯一の出所であり、手順で使う主語はここに定義済みのものに限る。ラベルを太字などで装飾しない。
- 手順：トップレベル見出し「手順」の下に各段階を小見出しで置く（下記「手順の記述規約」）。
- 付録：テンプレート・文例を置き、本文から番号で参照する。

## 手順の記述規約

- 1文＝1動作。主語（役割の代名詞）＋動詞で書く。主語は「役割と責任」に定義済みの代名詞のみを使う。
- 主語が不足したら、逆に「役割と責任」に役割を追加する。手順に未定義の主語を登場させない。
- 権限・格の整合：動作の相手の格に応じた主語にする。例：部門長への正式依頼は責任者名義。日常の照会は、あらかじめ定めた窓口へ担当部署が取り次ぐ（相手が上位職なら、発信主体も相応の職位にする、または事前に定めた窓口経由にする）。
- 重複を作らない：同じ連絡・処理を二重に定義しない。重複しそうなときは「1つに絞る」か、「経路・条件で内容を分離」する（例：受付連絡はフォーム経由＝自動返信、それ以外＝担当者が同趣旨を送付、で一本化）。
- 適用条件を明示する：ルールが一部の場合にだけ効くなら「〜の場合は」と条件を書く。
- 実装詳細を書かない：ローカルパス・特定システム名など環境依存の具体は避け、一般的表現（「組織内限定で管理」等）にする。
- 意思決定は権限とエスカレーション基準で示す。標準案件は定義した役割内で完結させ、例外案件のみ上位へ上げる。

## 体裁と番号

- 見出しは名詞句のみ（括弧書きの副題・確認日・「案」「ドラフト」「暫定」等のヘッジ語を付けない。[[living-doc-structure]] と同根）。
- 見出しなどのスタイル指定以外の文字修飾（太字・斜体・下線・上付き・下付き）を本文に使わない。強調は語順・見出し・箇条書きで表す。
- 表は使わない。手順・一覧は箇条書きまたはプロースで表現する。
- 番号は階層で統一し、末尾にピリオドを付ける：トップレベル `1.` `2.` …、小見出し `4.1.` `4.2.` …、付録 `5.1.` …。本文からの参照も同じ書式（`（下記 4.2.）`）。
- 引用文献は `[1]` のスタイルで記載する。

## メタデータと文書管理

- 文書冒頭はタイトルとサブタイトルで構成する。タイトルは文書名のみとし、発出元部門・組織名を含めない。
- サブタイトルに発出元部門（発行部署）と日付2行（`作成日：` / `改訂日：`。表記の正本は `instructions/principles.md`）を記載する。これ以外のメタデータ（版番号等）は持たない。
- 版管理（版番号・改訂履歴）は行わない。改訂時は改訂日だけを更新する。
- 承認ワークフローを文書に埋め込まない。レビュー・承認は運用側で行い、手順書本文には書かない。

## 配置とスコープ

- 正しくスコープされたサブプロジェクト／場所に置く。名称が似た別物と混同しない（例：研究立案の相談窓口と、患者対応の相談窓口はフォルダを分ける）。
- 個別事案・個人情報（PHI相当）は手順書に載せず、gitignore 対象のサブフォルダまたは該当案件フォルダで管理する。

## チェックリスト

- [ ] 目的は1文か。ねらい・注意事項・背景を混ぜていないか。
- [ ] 制度・背景の解説セクションを置いていないか。
- [ ] 役割は「役割と責任」で代名詞定義され、手順の全主語がそこに定義済みか。
- [ ] 各手順が「主語＋動作」で書かれ、権限・格が相手に整合しているか。
- [ ] 重複した連絡・処理がないか。ルールに適用条件が明示されているか。
- [ ] 見出しスタイル以外の文字修飾（太字・斜体・下線）を使っていないか。
- [ ] 表を使っていないか。見出しは名詞句か。番号は末尾ピリオドで階層統一か。
- [ ] タイトルは文書名のみか。発出元部門と作成日・改訂日をサブタイトルに置いているか。
- [ ] 版管理・承認ワークフローを埋め込んでいないか。
- [ ] 配置先のスコープは正しいか。個別の個人情報を含めていないか。
