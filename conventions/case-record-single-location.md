# 案件情報の保管場所

案件（出張・イベント・治験・面談・申請など、始まりと終わりのある1つの仕事）の情報は、**1案件＝1フォルダ**に集約する。同じ案件の情報を2つ以上のプロジェクトに分けて置かない。

## 決め方

「その案件は誰のものか」ではなく「**その案件を主催・所管しているプロジェクトはどれか**」で決める。

- 案件フォルダ ＝ その案件を所管するプロジェクトの配下（例: ある学会の出張なら、その学会を扱うプロジェクトの `<年>-<イベント>/`）。
- 手配・精算・事務処理を代行しただけの案件も、**情報は案件フォルダに置く**。代行した側のプロジェクトには置かない。

判断に迷ったら「半年後にこの案件を再開するとき、最初に開くフォルダはどこか」を考える。そこが案件フォルダである。

## 案件フォルダに入れるもの

その案件でしか使わない一次情報・記録すべて。

- 旅程・スケジュール・行程
- 予約と決済の記録（確認番号・金額・支払方法）
- チェックリスト・台帳・領収書
- 相手方とのやり取りの要点・議事録
- その案件固有の action-items

## 案件フォルダに入れないもの

- **再利用する仕組み**（スクリプト・スキル・テンプレート生成器）→ 仕組みを所管するプロジェクト。案件フォルダからはパスで参照する。
- **複数案件に共通する手順・ルール**（年次で繰り返す手続き、法令・規程の抽出）→ その案件群を所管するプロジェクトの `docs/`。案件フォルダには置かない。
- **一次データが別にあるもの**（スプレッドシート・Google Doc・API レスポンス）→ 正本はそこ。案件フォルダにはリンクと、そこから読んだ内容の要点だけを置く。

仕組みと案件データを分けるのは、仕組みが次の案件でも使われるから。案件フォルダに仕組みを置くと、次の案件でコピーが生まれる。

## やってはいけないこと

- 同じチェックリスト・同じ金額・同じ日程を2箇所に書く。**必ずズレて、どちらが正しいかを確認する将来の作業が発生する。**
- 「代行した側にも控えを置いておく」。控えは重複であって保険ではない。必要なのはパス1行の参照。
- 案件フォルダを跨いで「まとめ表」を作る。集約が必要なら各案件フォルダを参照するリンク集に留め、値を写さない。

## 既存の重複を見つけたときの手順

1. どちらを案件フォルダにするか上の基準で決める。
2. 残す側に、消す側の**固有情報だけ**を畳み込む（同じ内容は畳み込まない）。
3. 消す側を削除する。参照していた箇所を新しいパスに書き換える。
4. 案件フォルダの `CLAUDE.md` または `README.md` に「この案件の情報は本フォルダに集約する」と1行書き、統合した日付と統合元を残す。
5. 過去の work-log は歴史記録なので書き換えない。
